# 에이전트 브라우저와 네이티브 다이얼로그

`window.alert`, `window.confirm`, `window.prompt` 가 열렸을 때 에이전트 자동화가 어떻게 되는지 네 도구에서 직접 재본 기록이다. 도구 비교 전반은 [에이전트 브라우저 자동화 비교](./에이전트%20브라우저%20자동화%20비교.md)에 있고, 이 문서는 다이얼로그 한 지점만 파고든다.

측정 환경은 ego lite 0.4.7.4(`ego-browser` 스킬 v1.2.3)와 Orca 1.4.197 이다. Claude in Chrome 과 Playwright 는 공식 문서 근거만 있고 직접 재지 않았다. Aside 는 설치하지 않아 재보지 못했고 공개 문서에도 다이얼로그 언급이 없어 미측정으로 남긴다.

## 한눈에 비교

|                  | 멈추는가       | 원인                          | 에이전트가 스스로 푸는가                     | 근거     |
| ---------------- | ---------- | --------------------------- | ---------------------------------- | ------ |
| ego lite         | 멈춘다        | 태스크 스페이스 소유권이 사용자에게 넘어간다    | 못 푼다. 문서는 가능하다고 하지만 수십 ms 안에 막힌다   | 직접 측정  |
| Claude in Chrome | 멈춘다        | 모달이 Chrome 이벤트 루프를 막는다      | 못 푼다. 확장에 다이얼로그를 닫는 API 가 없다       | 공식 문서  |
| Orca 내장 브라우저     | 멈춘다        | Electron 네이티브 모달이 렌더러를 막는다  | 못 푼다. `dialog accept` 가 창을 보지 못한다  | 직접 측정  |
| Playwright       | 멈추지 않는다    | 핸들러가 없으면 전부 자동 dismiss      | 푼다. `page.on('dialog')` 에서 accept  | 공식 문서  |
| Aside            | 미측정        | 공개 문서에 언급 없음                | 미확인                                | 없음     |

증상은 셋이 같지만 원인이 다 다르다. 그래서 회복 경로의 품질도 갈린다.

Aside 는 Chromium 기반 별도 브라우저이고 `aside repl` 로 페이지에 JS 를 돌리는 구조라 ego lite 와 같은 부류일 가능성이 있다. 다만 확인하지 않은 추측이라 표에는 미측정으로만 남겼다. 재볼 기회가 생기면 `alert` 을 비동기로 띄운 뒤 REPL 명령이 계속 통하는지, 그리고 CLI 가 사람에게 확인을 넘기는지 두 가지만 보면 된다.

## 1. ego lite, 소유권을 사용자에게 넘긴다

다이얼로그가 열리면 그 태스크 스페이스의 `ownership` 이 `agentDelegatedToUser` 로 바뀐다. 에이전트가 `handOffTaskSpace()` 를 직접 부른 것과 같은 상태이고, CLI 도 평소의 핸드오프 안내 문구를 그대로 낸다. 오류가 아니라 정식 상태 전이다.

`confirm` 을 띄운 스페이스와 미리 무력화한 스페이스를 나란히 두면 차이가 분명하다.

```
16 native dialog behavior check  agentDelegatedToUser
17 dialog probe 2               agentDelegatedToUser
18 dialog probe 3               agentDelegatedToUser
19 dialog probe 4               agentDelegatedToUser
20 dialog probe 5 (사전 무력화)     agent
```

### 문서가 안내하는 경로에 닿지 못한다

`ego-browser` 스킬 문서(`SKILL.md` 49~50행)는 이렇게 안내한다.

> `pageInfo()` 가 `{ dialog: ... }` 를 반환하면 `cdp('Page.handleJavaScriptDialog', { accept: true })` 로 처리한 뒤 페이지 JS 를 실행하라.

실제로는 그 사이에 제어권이 넘어간다. 유예 시간도 일정하지 않다.

| 실험              | 다이얼로그 인지                   | 제어권 이전                            |
| --------------- | -------------------------- | --------------------------------- |
| alert           | `pageInfo()` 가 약 1.6초간 반환  | 약 1.8초 뒤 명령 차단                    |
| confirm         | 같은 정보 반환                   | 약 40ms 뒤 `handleJavaScriptDialog` 거부 |

40ms 는 관측하고 판단해서 호출할 수 있는 시간이 아니다. 문서가 낡았거나 자동 위임이 문서보다 이르게 도는 쪽인데, 어느 쪽이든 지금은 그 경로를 쓸 수 없다.

### 위임된 스페이스는 정리도 안 된다

`completeTaskSpace(id, { keep: false })` 는 문서상 사용자 소유 스페이스를 claim 한 뒤 닫는다. 그런데 다이얼로그로 위임된 스페이스에서는 같은 하드 스톱에 걸려 실패한다. 에이전트 소유로 남아 있던 20번만 닫혔고 16~19번은 사람이 정리해야 했다. 스스로 만든 뒤처리조차 못 하는 상태가 된다.

### 통하는 대응은 사전 무력화뿐이다

다이얼로그를 처리하려 하지 말고 열리지 않게 만든다. 아래 방식은 제어권이 유지되는 것을 확인했다.

```js
await cdp('Page.addScriptToEvaluateOnNewDocument', {
  source: "window.alert = () => {}; window.confirm = () => true; window.prompt = () => ''"
})
await gotoAndWait(url, { timeout: 20 })
```

`js()` 로 덮어쓰는 것과 다르다. `addScriptToEvaluateOnNewDocument` 는 새 문서마다 다시 주입되므로 이동과 새로고침을 넘어 살아남는다. 페이지 안에서 덮어쓰면 다음 이동에서 원래 함수가 돌아온다.

## 2. Claude in Chrome, 이벤트 루프가 막힌다

공식 문서의 "Browser not responding" 항목에 그대로 있다.

> Check if a modal dialog (alert, confirm, prompt) is blocking the page. JavaScript dialogs block browser events and prevent Claude from receiving commands. Dismiss the dialog manually, then tell Claude to continue.

ego lite 와 결과만 같고 성격은 다르다. ego lite 는 의도된 소유권 이전인데 이쪽은 구조적 한계다. 모달이 Chrome 이벤트 루프를 막으면 네이티브 메시징으로 오는 명령이 조용히 쌓이고 응답이 돌아오지 않는다. 확장에는 JS 다이얼로그를 닫는 API 자체가 없으니 사람이 누르는 것 외에 방법이 없고, 문서도 그렇게 안내한다.

## 3. Orca 내장 브라우저, Electron 제약이 겹친다

Electron 기반이라 셋 중 어느 쪽과도 다르게 움직인다.

```
window.prompt('x','d')  →  예외: prompt() is not supported.
window.alert('x')       →  네이티브 모달, 사람이 눌러야 반환
window.confirm('x')     →  네이티브 모달, OK 를 누르면 true
```

`prompt` 는 다이얼로그가 열리는 게 아니라 호출 자체가 실패한다. Electron 이 `window.prompt` 를 지원하지 않기 때문이다. 웹앱이 `prompt` 를 쓰는 경로는 이 브라우저에서 자동화도 수동 확인도 불가능하다.

### 노출된 dialog 명령이 창에 닿지 않는다

Orca CLI 에는 `dialog accept` 와 `dialog dismiss` 가 있다. 실제로 `confirm` 이 열린 상태에서 불러 보면 이렇다.

```
dialog 열림   ~501.15
accept 호출    501.439
accept 응답    503.015  →  CDP error (Page.handleJavaScriptDialog): No dialog is showing
```

에러 반환에 1.6초가 걸렸고 내용은 다이얼로그가 없다는 것이었다. Electron 이 띄운 네이티브 모달이 CDP 시야 밖에 있어서, CDP 로 내려가는 이 명령은 창을 보지 못한다. 명령이 존재하는데 이 상황에서는 아무 일도 하지 않는다.

### 막힌 탭은 탭을 닫아야 회복된다

`confirm` 을 한 번에 세 번 연속 호출하자 그 탭의 명령이 `The Orca runtime closed the connection before responding` 로 끊겼다. 이후 그 탭의 `eval` 과 `dialog dismiss` 가 모두 실패한 반면 `tab list` 는 정상이었다. 런타임은 살아 있고 그 탭만 막힌 상태다. 결국 탭을 닫아서 풀었다.

### 측정이 사람 클릭에 오염됐다

한 가지는 확정하지 못했다. 측정 중에 Orca 창에 모달이 떠서 내가 계속 확인 버튼을 눌렀다. 그래서 `confirm` 이 1.4초와 2.8초 뒤 `true` 가 된 것도, `alert` 이 291ms 만에 반환된 것도 도구의 동작이 아니라 내 반응 시간이다. 처음에는 이걸 자동 accept 로 잘못 읽었다.

사람이 아무도 누르지 않을 때 Orca 가 결국 스스로 처리하는지는 재지 못했다. 확정된 것은 두 가지다. 열려 있는 동안 그 탭의 자동화가 막힌다는 것, 그리고 `dialog accept` 로는 풀 수 없다는 것이다.

## 4. Playwright, 유일하게 안 멈춘다

기본값이 반대다.

> If there is no listener for `page.on('dialog')`, all dialogs are automatically dismissed.

`confirm()` 은 `false`, `prompt()` 는 `null` 이 되고 스크립트는 그대로 진행된다. 대신 함정이 있다.

> `page.on('dialog')` listener **must handle** the dialog. Otherwise your action will stall.

핸들러를 등록해 놓고 accept 나 dismiss 를 부르지 않으면 그때는 멈춘다. Playwright 에서 멈췄다면 기본 동작이 아니라 핸들러를 잘못 쓴 결과다.

## 측정 방법

이 계열을 다시 잴 때 쓸 수 있는 절차라 남긴다. 두 가지가 없으면 관측 자체가 안 된다.

**다이얼로그는 비동기로 띄운다.** `eval` 이나 `js` 로 `window.confirm('x')` 를 그냥 부르면 그 호출이 다이얼로그에 막혀 결과가 돌아오지 않는다. 관측할 기회가 사라진다.

```js
await js("setTimeout(() => { window.__c = window.confirm('probe') }, 100)")
```

`setTimeout` 으로 미뤄 두면 호출은 즉시 반환되고, 다이얼로그가 열린 상태에서 다른 명령을 보내 볼 수 있다.

**결과는 파일에 적는다.** 하드 스톱이 걸리면 CLI 가 안내 문구만 남기고 그때까지의 표준 출력을 통째로 버린다. 타임라인을 잃는다.

```js
import fs from 'node:fs'
const log = (m) => fs.appendFileSync(LOG, Date.now() + ' ' + m + '\n')
```

`pending` 같은 초기값을 미리 넣어 두는 것도 중요하다. `window.__c = null` 로 시작하면 `null` 이 dismiss 결과인지 아직 안 끝난 상태인지 구분되지 않는다. Orca 의 `prompt` 를 처음에 dismiss 로 잘못 읽은 게 이 때문이었다.

## 실무 규칙

- 다이얼로그를 쓰는 화면을 에이전트로 검증할 때, 도구를 안 가리고 통하는 방법은 열리기 전에 무력화하는 것뿐이다. Playwright 는 이게 기본이고 ego lite 는 `addScriptToEvaluateOnNewDocument` 로 만들 수 있다.
- 다이얼로그 자체가 검증 대상이면 막지 말고 핸드오프를 받아들인다. ego lite 는 사용자에게 무엇을 누를지 알린 뒤 사용자가 계속하겠다고 답하면 `takeOverTaskSpace()` 로 이어받는 절차가 있다.
- Orca 내장 브라우저는 `prompt` 를 쓰는 화면에 아예 쓸 수 없고, 모달이 뜨면 탭을 닫는 것이 유일한 회복이다.
- 새 화면을 자동화하기 전에 그 경로에 `confirm` 이 있는지 먼저 본다. 있으면 도구 선택이 달라진다.

## 읽고 남은 생각

- **사람의 브라우저를 빌려 쓰는 도구일수록 모달에서 사람을 필요로 한다.** [비교 문서](./에이전트%20브라우저%20자동화%20비교.md)에서 백그라운드 실행 가능성을 가른 축이 그대로 여기서도 갈린다. 아무것도 안 빌리는 Playwright 만 모달을 혼자 처리하고, 나머지 셋은 전부 사람 손을 부른다. 우연이 아니라 같은 설계 결정의 다른 얼굴이다.
- **Playwright 의 자동 dismiss 는 편리한 만큼 조용히 위험하다.** 핸들러를 안 붙이면 모든 `confirm` 이 `false` 로 처리된다. 테스트는 통과하는데 사용자가 확인을 누르는 분기는 한 번도 안 밟힌다. 삭제 확인 같은 곳에서는 정확히 반대쪽만 검증하는 셈이다. 다이얼로그가 있는 경로는 핸들러를 명시적으로 붙여야 한다.
- **문서와 런타임이 어긋난 사례를 하나 확보했다.** ego lite 스킬 문서는 에이전트가 다이얼로그를 처리하라고 안내하는데 런타임은 40ms 안에 그 권한을 회수한다. 스킬 문서를 사실로 두고 코드를 짜면 닿지 않는 분기를 만든다. 도구의 안내문은 시작점이지 근거가 아니다.
- **관측자가 화면을 공유하면 측정이 오염된다.** 내가 누른 클릭을 도구의 자동 처리로 읽었다. 사람과 에이전트가 같은 브라우저를 보는 구조에서는 이 오염이 기본값이다. 사람 개입이 섞였는지부터 확인해야 하고, 확인이 안 되면 그 수치는 결론으로 못 쓴다.
- **같은 증상을 원인 없이 묶으면 대응이 틀린다.** 넷 다 "알럿에서 멈춘다" 로 보이지만 하나는 의도된 위임, 하나는 이벤트 루프 차단, 하나는 Electron 모달, 하나는 사실 안 멈춘다. 원인이 다르니 회복도 다르다. ego lite 는 이어받는 절차가 있고 Claude in Chrome 은 수동 안내뿐이며 Orca 는 탭을 버려야 한다.
- **에이전트 시대에는 `confirm` 을 쓰는 UI 자체가 부채다.** 사람만 있을 때는 값싼 확인 수단이었는데, 자동화가 들어오면 도구마다 다른 방식으로 깨진다. 새로 만드는 화면에서는 인앱 모달로 두는 편이 자동화 가능성 면에서 낫다.
