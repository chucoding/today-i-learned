# Claude 프롬프트 엔지니어링

## 메모리 관리
### `CLAUDE.md`
Claude가 세션 시작 시 자동으로 읽는 마크다운 파일

#### 포함할 가치가 있는 것
- 명령어(빌드, 테스트, 린트, 로컬 실행 방법)
- 규칙(명명, 오류 처리, 파일 레이아웃, "X를 사용하고 Y는 사용하지 않습니다" 결정.)
- 3문장으로 된 아키텍처(주요 부분이 무엇이고 어떻게 통신하는지.)
- 하드 제약(예: "테스트에서 프로덕션 데이터베이스에 절대 쓰지 마세요", "모든 API 경로에 인증 미들웨어가 필요합니다", "generated/를 편집하지 마세요".)
- 알려진 함정(모든 새 엔지니어가 걸려드는 문제.)

#### 포함할 가치가 없는 것
- 전체 API 문서 (Claude는 코드를 직접 읽을 수 있습니다).
- 변경 로그 또는 히스토리.
- 파일 트리에서 이미 명백한 모든 것.
- 팀이 실제로 따르지 않는 열망적인 규칙.

#### 업데이트 빈도
- 이를 사양이 아닌 살아있는 온보딩 문서로 취급할 것
- Claude가 두 번 뭔가 잘못할 때
- 규칙이 변경될 때(예: 새 프레임워크, 테스트 러너, 또는 린트 규칙 세트.)
- 분기별 검토(오래된 지침은 없는 것보다 나쁘므로 오래된 항목을 삭제)


### 로드 방식 
- 시스템 프롬프트 -> `CLAUDE.md`(사용자 메시지로 Claude에 전달)
- 요약이나 자르기가 없으며, 각 턴마다 디스크에서 다시 읽지 않음.
- 세션 중에 파일을 편집하면 `/compact`를 실행하거나 `/memory`를 통해 열 때 변경 사항이 적용되며, 그렇지 않으면 다음 세션에 적용됨

### 비용
- 세션의 첫 요청은 파일의 전체 입력 토큰 가격을 지불
- 약 5분 이내의 후속 요청은 캐시에 도달하여 훨씬 낮은 캐시 읽기 요금으로 청구됨.
- `CLAUDE.md`의 모든 변경은 캐시를 무효화하고 다음 요청은 전체 가격을 지불
-  각 라인은 비용을 들일 가치가 있어야 함.(대략 200줄 미만 추천)

### 초기 셋팅 (`/init` 실행)
- Claude는 코드베이스를 탐색하고 CLAUDE.md를 작성함. 
- 빌드 명령어, 테스트 명령어, 구조 개요, 감지된 규칙을 포함

## 질문 방법
Claude가 실제 코드베이스를 읽고 편집할 때 가장 중요한 습관

1. 오류를 그대로 제공하기(요약하지 말고 전체 스택 트레이스 제공)
2. Plan Mode로 큰 작업의 범위 정하기(2개 이상의 파일을 건드리는 모든 작업)
- ex. "공개 API에 속도 제한을 추가하는 방법을 계획하세요. 아직 아무것도 변경하지 마세요."
- 계획을 검토하고, 대화에서 조정한 후, 모드를 전환하고 "1단계를 수행하세요"라고 말하세요. 이는 오해가 12개 파일 diff로 변하기 전에 포착합니다.
3. 대화당 한 작업(긴 세션은 잡음을 축적)

 
## 명령어
- 시작 CLAUDE.md 생성 `/init`
- Claude가 사용 중인 메모리 확인 `/memory`
- 프로젝트 메모리는 유지하면서 새로 시작 `/clear`
- 프롬프트에서 특정 파일 참조 `@path/to/file`
