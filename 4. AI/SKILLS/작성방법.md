# 스킬 작성 방법
스킬을 직접 만들 때 어디에 무엇을 적을지에 대한 규칙. 트리거 동작은 [자동 트리거](자동트리거.md) 참고.

## 실행 방식은 스킬이 아니라 진입점에 적는다
스킬을 서브에이전트로 떼어 돌리고 싶을 때 `"이 스킬은 서브에이전트로 실행한다"`를 SKILL.md 본문에 적기 쉽다. 동작하지 않는다.

```
세션 시작   ->  description 목록만 로드
매칭        ->  Skill 도구 호출 -> 본문 전체 로드   <- 여기서 그 문장을 읽는다
```

문장을 읽는 시점에 이미 메인이 본문을 다 로드한 뒤다. 그 뒤에 서브에이전트를 띄우면 같은 스킬을 두 번 읽는다.

실측 예 — 워크벤치 스킬을 서브에이전트로 돌리게 만든 세션:

```
10:19:43  메인이 스킬 로드              컨텍스트 비용 1회
10:21:04  메인이 서브에이전트 스폰
          서브가 같은 스킬을 다시 로드   컨텍스트 비용 2회
```

| 적는 위치 | 읽히는 시점 | 결과 |
|---|---|---|
| SKILL.md 본문 | 스킬 로드 **후** | 늦음. 컨텍스트 중복, 모델이 재위임을 선택해야 성립 |
| 지시문 파일(AGENTS.md 등) | 스킬 선택 **전** | 제때. 라우팅을 정하는 층 |
| 사용자에게 위임 | 매번 | 같은 판단 반복, 잊으면 조용히 직렬로 회귀 |

### 속성과 정책을 나눈다
- **스킬은 속성만 선언한다** — 쓰기 범위가 무엇인지, 다른 작업과 자원이 겹치는지, 결과를 누가 소비하는지. 즉 "떼어서 돌려도 안전하다"는 근거
- **지시문 파일은 정책을 정한다** — "이 작업에서는 저 스킬을 떼어서 돌리고 메인은 기다리지 않는다"

이 분리에는 실용적 이득이 하나 더 있다. **남이 만든 플러그인 스킬은 고칠 수 없지만 고칠 필요도 없다.** 그 스킬을 어떻게 돌릴지는 내 지시문 파일에 쓰면 되고, 스킬 본문은 자기 절차만 알면 된다. 반대로 스킬에 오케스트레이션을 심으면 스킬끼리 서로를 알아야 해서 결합이 생긴다.

### 곁들여 알아둘 것
서브에이전트를 띄운 **직후에 사용자에게 질문하지 않는다.** 스폰은 몇 초에 끝나고 백그라운드로 넘어가는데, 바로 뒤에 질문을 붙이면 사람 대기가 임계경로에 들어와 병렬로 벌어둔 시간이 그 자리에서 사라진다. 물어볼 것은 조사 결과와 함께 한 번에 묻는다.
