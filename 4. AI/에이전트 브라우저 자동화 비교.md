# 에이전트 브라우저·컴퓨터 자동화


|          | Orca computer use          | Claude in Chrome                        | Playwright                  | ego (lite)               |
| -------- | -------------------------- | --------------------------------------- | --------------------------- | ------------------------ |
| 제어 대상    | macOS 네이티브 앱 창·컨트롤         | 내가 쓰는 Chrome 탭                          | 자동화 전용 브라우저 프로세스            | 전용 Chromium 앱            |
| 제어 경로    | 접근성(AX) 트리 + 좌표 폴백         | 확장 + CDP(debugger 권한)                   | 드라이버 프로토콜(CDP/WebKit/Gecko) | 페이지 안에서 도는 JS 도구         |
| 지시 주체    | 모델                         | 모델                                      | **코드**                      | 모델(단, 실행 단위가 JS 덩어리)     |
| 로그인 세션   | 실제 앱 세션 그대로                | 실제 브라우저 세션 그대로                          | 없음 (`storageState` 로 주입)    | Chrome 데이터 마이그레이션으로 상속   |
| 사용자 방해   | 큼 (화면, 포커스를 공유)            | 큼 (내 탭에서 클릭이 일어남)                       | 없음                          | 낮음 (Space 로 격리)          |
| 백그라운드 동작 | 사실상 불가 (키보드 포커스와 클립보드를 공유) | 조건부 (실제 마우스는 안 뺏지만 같은 Chrome 창의 탭이 전환됨) | 가능 (headless 기본, 완전 분리)     | 가능 (Space 로 격리, 내 탭과 무관) |
| 재현성      | 낮음                         | 낮음                                      | **높음**                      | 중간                       |
| 플랫폼      | macOS(접근성·화면기록 권한)         | Chrome/Edge/Chromium, WSL 미지원           | 전 플랫폼 + CI                  | macOS만 (Windows 로드맵)     |
| 비용·라이선스  | Orca (MIT)                 | Anthropic 유료 플랜(Pro/Max/Team/Ent)       | Apache 2.0                  | MIT                      |


> **재현성** = 같은 작업을 다시 돌렸을 때 같은 결과가 나오는가. `같은 지시가 같은 동작이 되는가(결정론)` × `시작 상태를 다시 만들 수 있는가(환경 재현)` 다. 낮으면 실패가 버그인지 모델이 이번에 다르게 판단한 건지 구분되지 않아 CI 에 넣을 수 없다.

## 1. Orca computer use

유일하게 **웹이 아닌 것**을 다룬다. `orca computer` 는 실행 중인 macOS 앱의 접근성 트리를 읽고 그 안의 요소를 조작한다.

```bash
orca computer permissions --json                 # 접근성 + 화면기록 권한 확인
orca computer list-apps --json
orca computer get-app-state --app com.spotify.client --json
orca computer click --app com.spotify.client --element-index 42 --json
printf '%s' "$TOKEN" | orca computer set-value --app ... --value-stdin --json
```

- 좌표 클릭이 아니라 **의미 기반 조작이 1순위**다. `click` / `set-value` / `perform-secondary-action` 을 먼저 쓰고, AX 대상이 없을 때만 창 좌표로 떨어진다
- `--element-index` 는 **가장 최근 `get-app-state` 결과에만 유효**하다. 화면 전환·스크롤·포커스 이동이 있었으면 스냅샷부터 다시 떠야 한다. 이게 이 계열의 근본 취약점이다
- 브라우저를 만지려고 이걸 쓰면 안 된다. Orca 는 워크트리마다 붙는 **내장 브라우저**가 따로 있고, 그쪽은 완전히 다른 명령 계열이다

```bash
orca snapshot                          # 접근성 스냅샷, @e1 @e2 같은 ref 를 돌려줌
orca click --element @e7
orca fill --element @e3 --value "hello"
orca eval --expression "document.title"
orca set device --name "iPhone 12"     # CDP 디바이스 에뮬레이션
```

즉 Orca 안에서도 **computer use(네이티브 앱)와 browser automation(내장 브라우저)은 별개**다. 흔히 헷갈리는 지점이라 구분해서 봐야 한다. Claude Code 자체에도 macOS 네이티브 앱용 computer use 가 따로 있어서, "computer use" 라는 말만으로는 어느 쪽인지 특정되지 않는다.

## 2. Claude in Chrome — 내 로그인 상태를 그대로 쓴다

가장 큰 차별점은 성능도 API 도 아니고 **"이미 로그인돼 있다"** 는 사실 하나다. Gmail·Notion·Jira·사내 어드민에 커넥터나 API 키 없이 바로 들어간다.

- 연결은 네이티브 메시징 호스트 파일 + 확장. `claude --chrome` 또는 `/chrome` 으로 켠다
- **API 키·장기 토큰으로 인증한 세션에서는 아예 꺼진다.** 확장이 그 자격증명으로 인증할 수 없기 때문. `/login` 한 직접 플랜이어야 한다
- 사이트별 권한은 확장 설정에서 관리한다. 여기서 허용하지 않은 도메인은 못 만진다
- plan mode 에서 **읽기 계열(`read_page`, `get_page_text`, `find`, 콘솔·네트워크 읽기, 스크린샷)은 프롬프트 없이 돌고, 상태를 바꾸는 호출(클릭·입력·이동·탭 관리·GIF 녹화)은 승인을 받는다.** `browser_batch` 는 안에 든 동작이 전부 읽기일 때만 무프롬프트
- 기본 활성화(`Enabled by default`)는 브라우저 도구를 항상 로드하므로 **컨텍스트를 상시로 먹는다.** 필요할 때만 `--chrome` 이 낫다

실무에서 실제로 부딪히는 함정 두 가지가 문서에 명시돼 있다.


| 증상           | 원인                                     | 대응                                      |
| ------------ | -------------------------------------- | --------------------------------------- |
| 브라우저가 응답을 멈춤 | `alert`/`confirm`/`prompt` 모달이 이벤트를 막음 | 사람이 직접 닫아야 한다. 애초에 dialog 를 띄우는 버튼을 피한다 |
| 긴 세션 중 연결 끊김 | 확장 서비스 워커가 idle 로 내려감                  | `/chrome` → Reconnect extension         |


보안은 이 도구의 상수다. 실제 로그인 세션 위에서 모델이 클릭하므로 **프롬프트 인젝션의 사고 반경이 곧 내 계정 전체**다. Anthropic 은 인젝션 분류기와 고위험 행동(결제·게시·개인정보 공유) 사전 확인으로 막고 있다고 밝히지만, 확장 탈취 연구도 공개돼 있다. 완화 장치이지 격리가 아니다.

## 3. Playwright — 유일하게 코드가 결정한다

나머지 셋과 범주가 다르다. **모델이 판단하지 않고 코드가 판단한다.**

```ts
await page.getByRole('textbox', { name: '이메일' }).fill('test@example.com');
await page.getByRole('button', { name: '로그인' }).click();
```

- `getByRole` 이 돌려주는 건 요소가 아니라 **"찾는 방법"** 이다. 액션 시점에 다시 조회하므로 리렌더링으로 DOM 이 갈려도 stale 하지 않다. 앞의 세 도구가 "스냅샷 → 인덱스 → 그 사이 화면이 바뀌면 깨짐" 인 것과 정확히 대비된다
- auto-waiting 이 모든 액션에 내장돼 `sleep` 이 필요 없다
- 로그인 세션이 **없다는 게 기본값**이다. `storageState` 로 명시적으로 주입한다. 불편한 만큼 CI 에서 재현된다
- Chromium/Firefox/WebKit 한 API, headless, 트레이스·HTML 리포트

에이전트 쪽으로 넘어오는 다리도 있다. `@playwright/mcp` 는 스크린샷이 아니라 **접근성 트리 스냅샷**을 모델에게 주는 MCP 서버다. 이걸 쓰면 Playwright 도 "모델이 지시하는" 축으로 옮겨간다 — 즉 두 축은 도구가 아니라 **사용 방식**의 문제다.

## 4. ego (lite) — 왕복을 줄이는 데 올인한 브라우저

Citro Labs 가 만든 Chromium 기반 별도 브라우저. 확장이 아니라 **앱 자체를 갈아끼운다.**

- 첫 실행 때 Chrome 데이터(쿠키·로그인·확장·북마크) 마이그레이션을 한 번 묻는다. 승인하면 에이전트가 **로그인 상태를 상속**한다. 데이터는 로컬에만 둔다
- **Spaces** — Space 마다 독립 에이전트/작업이 동시에 돈다. 내 탭과 격리돼서 열 개를 돌려도 내 작업을 방해하지 않는다. Claude in Chrome 이 내 브라우저를 점유하는 것과 가장 크게 갈리는 지점
- 연결은 `ego-browser` 스킬. `npx skills add citrolabs/ego-lite`. 셸을 쓸 수 있는 에이전트면 Claude Code·Codex·Cursor·Gemini CLI 등 가리지 않는다
- 도구는 `snapshot` / `fill` / `click` / `wait` / `navigate` / `capture` 여섯 개

설계의 핵심은 도구 목록이 아니라 **호출 방식**이다.

> "The agent writes a JavaScript snippet calling those tools, and `ego-browser` runs it on the page in one pass."

명령 하나 보내고 결과 보고 또 하나 보내는 루프 대신, 여러 단계를 묶은 **JS 스니펫 한 덩어리를 페이지에서 한 번에 실행**한다. 벤더는 이걸로 agent-browser 대비 최대 2.5~3.45배 빠르고 툴콜·토큰이 크게 준다고 주장한다. **자체 벤치마크이고 비교 대상도 자기들이 고른 것**이라 수치 자체는 걸러 봐야 하지만, 병목을 짚은 방향은 맞다.

한계도 분명하다. macOS 전용(Windows 대기자 명단), 브라우저를 통째로 바꿔야 하고, 홍보 문구에 있는 "경험 축적" 기능은 아직 미구현이다.

## 5. 내가 다른 일을 하는 동안 돌릴 수 있나

기준은 하나다. 에이전트가 도는 동안 내가 마우스를 잡고 다른 화면을 봐도 양쪽 다 안 망가지는가.

### Playwright, 신경 쓸 게 없다

headless 가 기본이라 창 자체가 없다. 별도 브라우저 프로세스에서 돌고 OS 입력 장치를 건드리지 않는다. `--headed` 로 띄워도 내 브라우저와 다른 프로필, 다른 창이라 서로 모른다.

### ego (lite), 이걸 노리고 만든 물건

Space 마다 에이전트가 따로 붙고 내 탭과 격리된다. 공식 소개도 "내 작업 흐름을 방해하지 않고 백그라운드 탭에서 클릭하고 입력하고 이동한다"는 것이다. 애초에 내 Chrome 이 아니라 별도 앱이라, 내가 Chrome 을 그대로 쓰는 한 간섭이 없다. **로그인 상속과 비방해를 동시에 가져가는 유일한 조합**이고, 이 도구의 존재 이유가 사실상 여기에 있다.

### Claude in Chrome, 다른 앱으로 옮기면 괜찮다

입력이 OS 커서가 아니라 **탭 단위로 들어간다.** `computer` 도구가 `tabId` 와 뷰포트 기준 좌표를 받는 데서 드러난다. 물리 마우스가 움직이지 않으니 내가 다른 앱에서 일하는 것은 문제가 없다.

걸리는 건 같은 Chrome 창을 계속 쓸 때다. 문서에 "browser actions run in a visible Chrome window in real time" 이라고 못박혀 있고, 에이전트가 연 탭은 세션에 묶인 탭 그룹으로 모인다. 그 사이 내가 에이전트가 쓰던 탭을 직접 조작하면 요소 참조가 깨진다. 실용적인 회피책은 에이전트용 Chrome 창을 따로 하나 띄워 두고 내 작업은 다른 창에서 하는 것이다.

### Orca computer use, 손을 떼고 있어야 한다

네 개 중 제약이 가장 크다. 세 가지가 겹친다.

- `type-text` 는 도움말 그대로 "current app focus" 에 입력한다. 그 사이 내가 다른 창을 클릭하면 그 텍스트가 내 창으로 들어갈 수 있다
- `paste-text` 는 네이티브 클립보드를 거친다. 내가 복사해 둔 내용이 덮어써진다
- 모든 동작 뒤에 기본으로 스크린샷을 찍는다(`--no-screenshot` 으로 끈다). 화면 기록 권한이 필요한 실제 화면 캡처다

`--restore-window`(대상 창을 앞으로 가져오기)가 필수가 아닌 옵션이라, 접근성 기반 `click` 이나 `set-value` 는 창을 안 꺼내고도 되는 경우가 있다. 그래도 키보드가 섞이는 순간 내 조작과 충돌한다.

참고로 Orca 내장 브라우저(`orca snapshot`, `orca click`)는 이야기가 다르다. 워크트리마다 붙는 별도 Chromium 창이라 방해가 훨씬 적다. 같은 Orca 안에서도 두 계열의 성격이 갈린다.

### 한 줄로

**내 것을 빌려 쓰는 도구일수록 백그라운드가 안 된다.** 내 키보드를 빌리면(Orca computer use) 최악, 내 브라우저를 빌리면(Claude in Chrome) 중간, 세션만 복사해 가면(ego lite) 괜찮고, 아무것도 안 빌리면(Playwright) 무관하다.

## 축으로 다시 보기

### 축 1 — 무엇을 제어하는가

```
OS 접근성 트리 ── Orca computer use      (앱이면 뭐든, 웹 밖까지)
브라우저 확장  ── Claude in Chrome        (내 세션 그대로, 사이트 권한으로 제한)
드라이버      ── Playwright              (깨끗한 컨텍스트, 완전 통제)
브라우저 자체  ── ego (lite)              (세션 상속 + 격리를 동시에)
```

아래로 갈수록 통제력과 재현성이 오르고, 위로 갈수록 **"사람이 실제로 쓰는 환경"에 가까워진다.** 로그인·SSO·MFA·사내 시스템처럼 재현 비용이 큰 환경일수록 위쪽이 이긴다.

### 축 2 — 누가 결정하는가

Playwright 만 코드가 결정한다. 그래서 **명세가 확정된 일**에 강하고, 명세가 없는 일에는 쓸 수 없다. 나머지 셋은 모델이 결정한다. 명세 없는 일을 할 수 있는 대신 **같은 입력에 같은 결과를 보장하지 않는다.** 회귀 테스트를 모델 자율 도구로 짜면 실패가 버그인지 흔들림인지 구분이 안 된다.

ego (lite) 는 이 축의 중간이다. **판단은 모델이 하되 실행 단위는 코드**다.

### 축 3 — 왕복 비용

에이전트 브라우저 자동화의 실제 비용은 클릭이 아니라 **루프**다.

```
스냅샷 → (모델 추론) → 툴콜 1개 → 스냅샷 → (모델 추론) → 툴콜 1개 → ...
```

단계마다 페이지 스냅샷이 컨텍스트로 다시 들어가므로 토큰이 단계 수에 비례해 붙는다. 대응은 셋 다 갖고 있다 — Claude in Chrome 의 `browser_batch`·`javascript_tool`, Orca 의 `eval`, ego (lite) 의 JS 스니펫. 다른 건 **그게 기본값이냐 예외냐**다. ego (lite) 는 이걸 기본 실행 모델로 잡았고, 나머지는 옵션으로 갖고 있다.

### 축 4 — 사고 반경


|                   | 잘못 눌렀을 때 벌어지는 일                       |
| ----------------- | ------------------------------------- |
| Playwright        | 격리된 컨텍스트가 더럽혀짐. 버리면 끝                 |
| ego (lite)        | 상속된 로그인 세션에서 실제 동작. Space 로 내 작업만 보호됨 |
| Claude in Chrome  | 내 실제 계정에서 실제 동작. 인젝션 표면이 열려 있는 모든 사이트 |
| Orca computer use | 브라우저 밖까지. 파일·메일·터미널 등 열려 있는 앱 전부      |


**로그인 상속은 기능이자 그대로 위험이다.** 편의와 사고 반경이 같은 물건이라 둘을 따로 조절할 수 없다.

| CI 에서 도는 회귀 테스트               | Playwright                    | 결정론·재현성이 전제                        |
| 방금 고친 화면 확인, 콘솔·네트워크 보고 코드 수정 | Claude in Chrome              | 코드↔브라우저 왕복이 한 세션에서 끝남              |
| 로그인 필요한 사내 툴에서 반복 입력          | Claude in Chrome / ego (lite) | 세션 상속. 내 브라우저를 계속 써야 하면 ego (lite) |
| 여러 사이트·작업 병렬 스크래핑             | ego (lite)                    | Spaces 병렬 + 왕복 절감                  |
| 브라우저로 안 되는 일 (네이티브 앱, 시스템 설정) | Orca computer use             | 유일한 선택지                            |
| 팀에 배포할 자동화                    | Playwright                    | 나머지는 macOS·개인 세션·개인 플랜에 묶임         |


## 읽고 남은 생각

- **"AI 브라우저 자동화" 를 하나로 묶어 비교하는 게 애초에 틀렸다.** Playwright 는 나머지 셋과 경쟁 관계가 아니라 보완 관계다. 대체 후보는 Claude in Chrome ↔ ego (lite) 두 개뿐이고, 갈림길은 성능이 아니라 **"내 브라우저를 내주느냐"** 다.
- **로그인 상속이 이 판의 실질적인 해자다.** 기능 목록은 넷이 거의 같다 — 스냅샷·클릭·입력·대기·캡처. 차이를 만드는 건 도구가 아니라 **세션이 어디서 오느냐**. API 커넥터 없이 사내 시스템에 붙을 수 있다는 게 Playwright 가 못 하는 유일한 일이고, 동시에 가장 위험한 일이다.
- **스냅샷 인덱스의 수명이 이 계열 전체의 공통 결함이다.** Orca 의 `--element-index`, ego 의 ref, Claude in Chrome 의 요소 참조 모두 "직전 스냅샷 기준"이다. Playwright 의 locator 가 조회를 액션 시점까지 미뤄서 이걸 구조적으로 푼 것과 대비된다. 에이전트 도구들이 아직 이 해법을 안 가져왔다.
- **성능 주장은 벤치마크가 아니라 아키텍처로 읽는 게 낫다.** 3.45배는 자체 측정이라 못 믿지만, "툴콜 왕복마다 스냅샷이 컨텍스트에 다시 들어간다" 는 구조는 사실이다. 그래서 어느 도구를 쓰든 **여러 단계를 한 번에 묶는 호출을 우선 쓰는 게 이득**이다. Claude in Chrome 이면 `browser_batch`, Orca 면 `eval`.
- **plan mode 의 읽기/쓰기 구분은 좋은 설계다.** "읽기는 무프롬프트, 상태 변경은 승인" 그리고 "읽기 도구라도 `save_to_disk` 나 `clear` 같은 플래그가 붙으면 승인" — 도구 이름이 아니라 **인자까지 보고 부작용을 판정**한다. 우리 쪽 툴 권한 설계에도 그대로 쓸 만한 기준이다.
- 넷 중 셋이 macOS 전용이거나 개인 플랜·개인 브라우저에 묶여 있다. **팀 자산이 되는 건 아직 Playwright 뿐**이라는 게 지금 시점의 결론이다.
- **로그인 상속과 비방해는 보통 맞바꾸는 관계인데 ego (lite) 만 둘 다 가져간다.** 내 세션을 쓰려면 내 브라우저를 빌려야 하고, 빌리면 내가 못 쓴다. 이 딜레마를 브라우저를 통째로 하나 더 두는 방식으로 푼 셈이다. 대가는 macOS 전용이라는 것과 평소 브라우저를 갈아타야 한다는 것이다.
