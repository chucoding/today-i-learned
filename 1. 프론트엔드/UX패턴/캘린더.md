# 캘린더
날짜·시간 피커의 팝업을 **언제 닫을지·어디에 배치할지·격자를 벗어난 값을 어떻게 다룰지**와, 직접 만들 때 걸리는 함정

## 닫는 시점은 "한 번 골라서 값이 완성되는가"로 갈린다
피커 팝업의 닫힘 정책은 취향이 아니라 **팝업의 구조**가 결정한다.

| 팝업 구조 | 한 번 선택하면 | 닫힘 정책 | 채택 |
|---|---|---|---|
| 단일 시각 리스트 (`10:00`, `10:30`, …) | 값이 **완성**됨 | 선택 즉시 닫기 | Atlassian, Fluent UI v9, Angular Material, Kendo `classic` |
| 시/분 분리 컬럼 | 값이 **미완성** (나머지 컬럼이 남음) | 자동으로 닫지 않음 | MUI X v8+, Ant Design, Kendo `modern`, Element Plus, Mantine |

Kendo UI가 이 대비를 한 컴포넌트 안에서 보여준다. `componentType="classic"`(단일 리스트)은 항목 클릭 즉시 닫고, `componentType="modern"`(시/분/초 컬럼)은 `Set` 버튼으로만 닫으며 **blur 에서조차 닫히지 않도록 명시적으로 막는다.**

## "마지막 단위를 고르면 닫기"는 폐기된 패턴이다
분리 컬럼에서 **분을 고르는 순간 닫는** 동작은 그럴듯해 보이지만, MUI X 가 v6/v7 에서 그렇게 하다가 v8 에서 **브레이킹 체인지로 되돌렸다.**

| 버전 | `DesktopTimePicker.closeOnSelect` | 문서상 동작 |
|---|---|---|
| v6 / v7 | `true` | "The picker will close when selecting the **minutes** or meridiem" |
| v8+ | **`false`** | "The picker will **not** close when selecting the minutes or meridiem" |

되돌린 이유가 이슈에 남아 있다.

> "I would remove this auto-close behavior **anywhere there is more than one widget**. So only keep it for the date picker." — MUI 공동창업자, [#9310](https://github.com/mui/mui-x/issues/9310)

> "I don't understand why selecting AM or PM validates the value, **I didn't press the OK button yet**." — [#8964](https://github.com/mui/mui-x/issues/8964)

시만 바꾸고 싶은 사용자가 매번 팝업을 다시 열어야 하는 것이 핵심 문제다. 같은 이유로 Ant Design 은 `picker="time"` 이면 `needConfirm` 이 **자동으로 `true`** 가 되어 확인 버튼이 붙는다.

## 날짜는 즉시 닫아도 되지만 시간·날짜시간은 아니다
MUI X v8+ 의 `closeOnSelect` 기본값이 이 구분을 그대로 보여준다.

| 컴포넌트 | 기본값 |
|---|---|
| `DesktopDatePicker` | `true` |
| `DesktopTimePicker` | `false` |
| `DesktopDateTimePicker` | `false` |

날짜는 셀 하나를 누르면 값이 완성되므로 즉시 닫아도 된다. 시간·날짜시간은 위젯이 둘 이상이라 아니다.

## 확인 버튼을 없앨 거면 닫는 경로를 먼저 확보한다
"확인/취소 버튼 제거"는 흔한 요구지만, 버튼이 **유일한 닫기 수단이었다면** 제거하는 순간 사용자가 갇힌다. 분리 컬럼 피커에서 자동 닫힘까지 없다면 닫는 경로가 하나도 안 남는다.

버튼을 없앨 때 최소한 이 세 가지는 있어야 한다.

- **트리거 재클릭** — 열기만 하고 토글이 아닌 경우가 많다. `setOpen(true)` 가 아니라 `setOpen(prev => !prev)`
- **바깥 클릭**
- **Esc** — 빠뜨리기 쉽다. 키보드만 쓰는 사용자에게는 유일한 탈출구다. 모달 안에서는 그냥 걸면 모달까지 같이 닫히므로 아래 [모달 절](#모달-안에서-여는-피커는-esc포털z-index-세-가지가-겹친다) 참고

접근성 문서들도 닫힘을 **사용자의 명시적 동작**에 묶는다. Kendo 는 팝업 탭 순서를 `시 → 분 → 초 → Cancel → Set` 으로 규정하고 팝업 안에 탭을 가둔다. Semrush Intergalactic 은 닫힘 트리거를 Enter(적용 후 닫기)와 Esc(값 변경 없이 닫기) 둘로만 정의한다.

실은 **표준 조합이 "분리 컬럼 + 확인 버튼"** 이다. 자동으로 안 닫으니 사용자가 "다 골랐다"고 말할 수단을 줘야 하고, 그게 확인 버튼이다. 확인 버튼을 없애면 그 자리를 위 세 경로가 메워야 한다.

| 라이브러리 | 확인 버튼 |
|---|---|
| MUI X v8 | 있음 |
| Ant Design | 있음 (`needConfirm` 자동 `true`) |
| Kendo `modern` | 있음 (`Set`) |
| Element Plus | 있음 |
| Mantine | 없음 (blur 만) |

> ⚠️ MUI 문서의 *"By default, it contains no action on desktop"* 문장을 "데스크톱엔 액션바가 없다"로 일반화하면 틀린다. v8 기준으로 그건 `DesktopDatePicker`·`DesktopDateRangePicker` 에만 해당하고, **시간 계열은 데스크톱에도 `['cancel', 'accept']` 가 기본**이다. 소스(`usePicker.tsx`)가 `closeOnSelect && !hasSeveralSteps` 일 때만 `[]` 를 돌려준다.

## 달력 행 수를 6주로 고정한다
달을 주 단위로만 채우면 월마다 **4~6행**이 되어, 이전/다음 달로 넘길 때 팝업 높이가 한 행(보통 40px)씩 널뛴다. 드롭다운이라면 위치까지 다시 계산돼 화면이 튄다.

남는 칸을 다음 달 날짜로 채워 **항상 6행**을 유지하면 높이가 고정된다. 디자인 시안도 대개 6행 기준으로 그려져 있다.

직접 만들 때만의 문제가 아니라 라이브러리도 옵션으로 갖고 있다. react-day-picker 의 `fixedWeeks` 가 같은 해법이다.

> "always display 6 weeks per month, which will **prevent the grid from changing its height while navigating the calendar**"

> "Since months can have between 4 and 6 weeks, you can use `fixedWeeks` with `showOutsideDays`"

빈 칸을 다음 달 날짜로 채우는 방식까지 같고, **바깥 날짜 표시(`showOutsideDays`)가 함께 켜져 있어야** 의미가 있다는 점도 같다. 참고로 shadcn/ui 의 `Calendar` 는 `showOutsideDays` 는 기본 `true` 지만 `fixedWeeks` 는 켜지 않는다.

## React 포털은 DOM 이 아니라 React 트리로 이벤트가 버블링된다
드롭다운을 `createPortal` 로 `body` 에 붙였더라도, **JSX 상 트리거의 자식으로 렌더했다면** 드롭다운 내부 클릭이 트리거의 `onClick` 까지 올라간다. DOM 트리만 보고 "포털이니 안 올라온다"고 판단하면 틀린다.

```tsx
<div onClick={() => setOpen(prev => !prev)}>   {/* 트리거 */}
  ...
  {open && createPortal(<Dropdown />, document.body)}  {/* 클릭이 위 onClick 까지 버블링 */}
</div>
```

트리거를 토글로 바꾼 순간 **드롭다운 안을 클릭할 때마다 닫히는** 버그가 된다. 포털 루트에서 `onClick`·`onMouseDown` 을 함께 끊거나, 포털을 트리거의 형제로 렌더한다.

여기까지는 **어디에 포털하든** 생기는 문제다. 포털 **대상을 어디로 잡을지**는 별개이고 모달 안에서 갈린다 — 바로 아래 절.

## 모달 안에서 여는 피커는 Esc·포털·z-index 세 가지가 겹친다
피커 단독으로는 멀쩡하던 코드가 **모달 안에 들어가는 순간** 깨진다. 모달도 오버레이라서 같은 자원(전역 키 이벤트, 포털 대상, 스태킹 컨텍스트)을 두고 부딪친다.

### Esc — `stopPropagation()` 으로는 모달이 안 막힌다
피커와 모달이 **둘 다 `document` 에 `keydown` 을 걸면** Esc 한 번에 피커도 닫히고 모달도 닫힌다. `stopPropagation()` 을 불러도 마찬가지다.

`stopPropagation()` 은 **다음 노드로의 전파**만 막고, **같은 노드에 등록된 나머지 리스너**는 그대로 실행된다. 둘 다 `document` 버블 단계에 있으면 애초에 "다음 노드"로 넘어갈 일이 없으니 아무것도 막지 못한다.

| 상황 | `stopPropagation()` | `stopImmediatePropagation()` |
|---|---|---|
| 자식 노드 → 부모 노드 리스너 | 막힘 | 막힘 |
| **같은 노드의 다른 리스너** | **안 막힘** | 막힘 |

같은 노드 안에서의 실행 순서는 **등록 순서**다. 모달이 먼저 열려 있으니 모달 리스너가 먼저 등록되고, 나중에 열린 피커는 순서를 뒤집을 방법이 없다. 그래서 단계를 바꾼다.

```ts
// 피커: capture 단계는 document 버블 단계보다 항상 먼저 실행된다
const handleKeyDown = (e: KeyboardEvent) => {
  if (e.key !== 'Escape') return
  e.stopImmediatePropagation()  // 뒤에 올 모달 리스너까지 전부 끊는다
  close()
}
document.addEventListener('keydown', handleKeyDown, true)
```

capture(document) → target → bubble(document) 순서라, capture 에서 잡으면 모달 리스너 차례가 오기 전에 이벤트가 끝난다.

> ⚠️ 열려 있는 동안 Esc 를 **페이지 전체에서** 삼킨다. React 17+ 는 이벤트를 `document` 가 아니라 **루트 컨테이너**에 위임하므로, `document` capture 에서 끊으면 안쪽 컴포넌트의 `onKeyDown` 도 실행되지 않는다. 피커가 최상위 오버레이일 때만 맞는 선택이다.

> 💡 모달을 `dialog.showModal()` 로 띄웠다면 Esc 는 리스너 이전에 **브라우저가 직접** 닫는다. 이건 리스너로 못 막고 `dialog` 의 `cancel` 이벤트에서 `preventDefault()` 해야 한다. `<dialog open>` (비모달)로 렌더했다면 네이티브 닫기 자체가 없어 해당 없음.

### 포털 대상 — `body` 로 고정하면 모달 포커스 트랩 밖으로 나간다
드롭다운을 잘림 없이 띄우려고 `document.body` 에 포털하는 건 맞지만, 모달 안에서까지 그러면 **모달 밖으로 나가버린다.** 포커스 트랩은 보통 모달 루트 기준 `querySelectorAll` 로 포커스 가능 요소를 모으므로, `body` 로 나간 드롭다운은 순회 대상에서 빠져 Tab 으로 도달할 수 없다.

앵커의 조상을 훑어 모달 안이면 **모달 루트**를, 아니면 `body` 를 쓴다.

```ts
anchor?.closest('dialog, [aria-modal="true"]') ?? document.body
```

모달 루트는 대개 overflow 클리핑이 없어서 `position: fixed` 배치가 그대로 유지된다.

### z-index — 앱 chrome 보다 위, 모달보다 아래
`body` 로 포털하면 인풋이 속한 스태킹 컨텍스트를 벗어나 **앱 헤더·탭바·사이드패널과 같은 평면**에 놓인다. 기본값을 앱 chrome 보다 위이면서 모달(예: `1300`)보다는 아래로 잡고, 조상에 더 높은 `z-index` 가 있으면 그 위로 올린다.

## 위·아래 어디에도 안 들어가면 "남은 공간만큼 잘라 스크롤"이 표준이다
드롭다운 배치는 보통 "아래 공간이 부족하면 위로 뒤집는다(flip)"까지만 구현한다. 그런데 **양쪽 다 부족한** 경우가 남는다. 이때 팝오버를 뷰포트 안으로 밀어 넣으면(clamp) 앵커인 **입력창을 덮어** 방금 고른 값이 보이지 않는다. 화면 밖으로 넘치는 것보다 나쁘다.

```ts
// 흔한 버그: 뷰포트 안으로만 맞추고 앵커와의 겹침은 보지 않는다
const top = placeAbove ? anchorRect.top - height - GAP : anchorRect.bottom + GAP
return clamp(top, PADDING, window.innerHeight - height - PADDING)  // ← 입력창 위로 올라온다
```

### 극단적인 화면만의 문제가 아니다
팝오버가 위 또는 아래에 들어가려면 `콘텐츠 높이 + 간격 + 뷰포트 여백` 이 필요하다. 6주 고정 캘린더(364px)에 간격 6·여백 8이면 **378px** 이다. 입력창 높이를 `A` 라 하면 양쪽 다 부족한 구간이 생기는 조건은

```
뷰포트 높이 V < 378 * 2 + A     // A = 38 이면 V < 794
사각지대 폭 = 794 - V           // 입력창이 이 구간에 있으면 발생
```

| 뷰포트 높이 | 사각지대 | 해당 환경 |
|---|---|---|
| 810px | 없음 | 1080p 최대화 |
| 780px | 14px | |
| 650px | 144px | 1366x768 노트북 |
| 490px | 304px | 1080p + 200% 확대 (WCAG 1.4.4) |

즉 **뷰포트 794px 미만이면 화면 세로 중앙의 입력창은 전부 걸린다.** 노트북과 확대 화면이 사정거리 안이라 "작은 화면은 무시"로 넘길 수 없다. [6주 고정](#달력-행-수를-6주로-고정한다)이 높이를 키우는 쪽으로 작용하는 것도 같이 봐야 한다 — 높이를 고정하면 위치 계산은 안정되지만 안 들어갈 확률은 올라간다.

### 표준 해법: 가용 공간을 실측해 `max-height` + 내부 스크롤
| 라이브러리 | 처리 |
|---|---|
| Floating UI | `size` 미들웨어가 `availableHeight` → `max-height` |
| Radix UI | `--radix-select-content-available-height` → `max-height` (내부는 Floating UI `offset→shift→flip→size`) |
| MUI | Menu paper `maxHeight: calc(100% - 96px)`, Popover paper `calc(100% - 32px)`, Autocomplete listbox `40vh + overflow:auto` |
| Polaris | `min(spaceBelow, desiredHeight)` + `max-height: 500px` + Scrollable `overflow-y: auto` |
| react-aria / React Spectrum | `Math.min(boundary.height - padding*2, maxHeight)` 를 인라인 `style.maxHeight` 로 |
| Carbon | `block-size: 336px` 고정 + `overflow: hidden` + `disableMobile: true` — 사실상 무대응 |
| Ant Design | DatePicker 는 뒤집기만 해서 잘림 (아래 참고) |

계산 방식이 두 갈래다. Floating UI·Radix·react-aria 는 **실측**(경계까지의 남은 픽셀), MUI 는 **고정 비율·상수**(`40vh`, `calc(100% - 96px)`)다. 실측이 정확하지만 측정 시점을 관리해야 하고, 상수는 단순하지만 앵커 위치를 반영하지 못한다.

Floating UI 문서는 콘텐츠를 줄일 수 없는 경우까지 명시한다.

> "If your floating element's content cannot be resized such as in the example, you can make the floating element scrollable with `overflow: scroll` (or `auto`). Ensure your CSS is using `box-sizing: border-box`!"

`box-sizing: border-box` 가 조건인 이유는 `max-height` 가 padding 을 포함해야 남은 공간과 계산이 맞기 때문이다.

Radix 는 같은 일을 CSS 변수로 노출한다.

> "You may also want to constrain its height to not exceed the viewport." — `max-height: var(--radix-select-content-available-height)`

### 잘렸으면 잘렸다고 보여준다
Radix 가 `Select.ScrollUpButton` 을 두는 이유가 이거다.

> "An optional button used as an affordance to **show the viewport overflow** as well as functionally enable scrolling upwards."

브라우저 기본 스크롤바에 맡길 수도 있지만, 스크롤바를 숨기는 디자인이면 잘린 사실 자체가 안 보인다. 어포던스는 스크롤 기능과 별개 항목으로 챙겨야 한다.

### 높이를 트리거로 모달 전환하는 표준은 없다
"짧으면 다이얼로그로 바꾸자"는 그럴듯하지만, 조사 대상 중 **높이 기반 자동 전환은 0건**이었다. 모달 전환 자체는 흔한데 기준이 전부 폭 또는 플랫폼이다.

| 사례 | 전환 기준 |
|---|---|
| MUI X DatePicker (Desktop ↔ Mobile) | `desktopModeMediaQuery` 기본값 `@media (pointer: fine)` — 포인터 정밀도 |
| React Spectrum tray | 폭 700px |
| Ant Design | "모바일은 `ant-design-mobile` 을 쓰라" (바텀시트) |
| Material fullscreen date picker | 앱이 테마로 선택 |

Material 이 높이에 실제로 대응하는 방식은 전환이 아니라 **축소**다 — `values-h360dp-land` 에서 날짜 셀을 48→40dp 로 줄인다.

### 접근성 최소선은 낮다
SC 1.4.10 Reflow 는 세로쓰기가 아닌 페이지에 **높이 256px 를 요구하지 않는다**("320x256 동시 충족"으로 읽으면 오독이다). 높이 400~520px 에서 팝오버가 안 들어가는 것 자체는 위반이 아니고, 위반이 되는 건 **콘텐츠가 잘려 도달 불가**해질 때다. 팝오버 안의 스크롤 컨테이너는 명시적으로 허용된다. 그래서 "잘라서 스크롤"이 근거상 가장 방어 가능한 선택이고, 모달 전환은 선택 사항이다.

### 직접 구현할 때의 함정 세 개
- **측정 기준을 `offsetHeight` 로 하면 복원되지 않는다.** `max-height` 를 걸면 그때부터 `offsetHeight` 가 잘린 높이라, 뷰포트가 다시 넓어져도 "이미 들어간다"고 판단해 작은 채로 남는다. 콘텐츠 높이 기준으로 재야 한다.
  ```ts
  // 잘린 뒤에도 원래 높이를 알 수 있다 (스크롤 높이 + 테두리·스크롤바)
  const natural = el.scrollHeight + (el.offsetHeight - el.clientHeight)
  ```
- **`max-height` 를 항상 걸면 안 된다.** 다 들어갈 때도 상한을 걸어두면 월 이동·뷰 전환으로 내용이 늘어날 때 잘린다. 게다가 `ResizeObserver` 로 재계산하는 구조라면 요소 크기가 상한에 묶여 변화가 감지되지 않는다. **제한이 필요할 때만** 지정한다.
- **팝오버 루트가 flex 컬럼이면 자식이 눌린다.** 스크롤이 아니라 콘텐츠가 찌그러진다. 스크롤되게 하려면 자식에 `flex-shrink: 0` 이 필요하다.

> ⚠️ 배경 탭에서는 `requestAnimationFrame` 이 멈춘다. 스크롤·리사이즈 핸들러를 rAF 로 스로틀했다면 **탭이 안 보이는 동안 재배치가 전혀 일어나지 않는다.** 헤드리스나 백그라운드 탭에서 검증하다가 "리사이즈에 반응하지 않는 버그"로 오진하기 쉽다(실제로 오진했다). `document.hidden` 을 먼저 확인할 것.

> 💡 부모에서 `iframe` 의 `height` 를 바꿔도 자식 `window` 에 `resize` 이벤트가 오지 않는다(실측). iframe 을 축소해 짧은 뷰포트를 재현하는 하네스로는 "열려 있는 동안의 리사이즈"를 검증할 수 없고, 크기별로 새로 마운트해서 확인해야 한다.

## 격자를 벗어난 분이 들어오면 스냅이 아니라 무효 처리가 표준이다
시간 피커는 보통 5분·15분 격자만 옵션으로 준다. 그런데 텍스트 입력을 함께 두면 사용자가 `14:37` 처럼 격자를 벗어난 값을 넣을 수 있다. 이때 값을 격자로 맞출지(스냅) 그냥 둘지가 갈리는데, **플랫폼과 라이브러리는 스냅하지 않는다.**

| 대상 | 격자를 벗어난 타이핑 값 처리 |
|---|---|
| HTML `<input type="time" step="900">` | 값을 보정하지 않고 `stepMismatch` 로 **무효** 표시. 보정은 `stepUp()`·`stepDown()` 을 호출할 때만 일어난다 |
| MUI X `TimeField` | `minutesStep` 을 벗어난 분을 입력하면 **테두리를 빨갛게** 표시하고 값은 그대로 둔다 |
| Ant Design TimePicker | `minuteStep` 은 목록에 **보이는 옵션만** 제어한다. 타이핑 값 처리는 문서화되어 있지 않다 |

`<input type="time">` 은 `min`·`max` 를 벗어난 값도 clamp 하지 않는다. 즉 플랫폼의 일관된 태도는 **사용자가 넣은 값을 조용히 고치지 않고, 틀렸다고 알린다** 는 것이다.

### 반올림 스냅은 단위를 넘는다
```js
Math.round(59 / 5) * 5   // → 60. 분에 60은 없다
```
5분 격자 목록(0~55, 12개)에서 스크롤 위치를 `selectedMinute / 5` 로 계산하는 코드가 있었다. 분이 58·59 인 값을 열면 index 가 **12** — 존재하지 않는 항목 — 이 됐다(실측). 격자에 맞추는 계산에는 `Math.min(55, ...)` 처럼 상한이 함께 필요하다.
