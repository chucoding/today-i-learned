# 오버레이 해제
열린 드롭다운을 **언제 닫을지**, 그리고 그 규칙을 **누가 정할지**. 표준이 정해주는 범위와 구현체 몫의 경계

배치를 다루는 문서는 [팝오버배치.md](./팝오버배치.md), 피커별 닫기 시점과 값 처리는 [캘린더.md](./캘린더.md)에 있다. 이 문서는 그 둘이 다루지 않는 것을 맡는다. 라우팅 전환과 뒤로가기, 화면을 숨긴 상태의 생명주기, 그리고 책임 경계다.

## 표준은 "닫기 요청"이라는 추상만 정의하고 목록은 플랫폼에 넘긴다
HTML 명세에 **close request** 라는 개념이 있다. 무엇을 닫는 것인지까지 정의 문장이 직접 열거한다.

> "In an implementation-defined (and likely device-specific) manner, a user can send a close request to the user agent. This indicates that the user wishes to close something that is currently being shown on the screen, such as a **popover, menu, dialog, picker, or display mode**."

`implementation-defined` 가 핵심이다. 무엇이 닫기 요청인지 규범적으로 열거하지 않고 예시만 든다.

> "Some example close requests are: The Esc key on desktop platforms. The back button or gesture on certain mobile platforms such as Android. Any assistive technology's dismiss gesture, such as iOS VoiceOver's two-finger scrub "z" gesture. A game controller's canonical "back" button, such as the circle button on a DualShock gamepad."

즉 Esc, Android 뒤로가기, VoiceOver 해제 제스처, 게임패드 back 버튼이 **하나의 추상 사건**이다. 앱은 계기를 열거하지 않고 `CloseWatcher` 를 등록한다.

Esc 를 언제 잡는지도 규정돼 있다. 흔히 틀리는 부분이다.

> "the user agent must interpret the key being pressed down as the close request, instead of the key being released. Thus, in the above algorithm, the "relevant events" that are fired must be the single keydown event."

`keyup` 을 듣는 구현은 명세와 어긋난다.

## 뒤로가기는 두 종류이고, 하나만 닫기 요청이다
같은 "뒤로가기"라도 사용자가 누른 것과 코드가 부른 것이 표준상 완전히 다르다.

| | Android 뒤로가기 버튼과 제스처 | `history.back()`, `router.back()` |
|---|---|---|
| 발생 주체 | 사용자가 UA 에 보내는 플랫폼 입력 | 페이지 스크립트 |
| close request 인가 | **예** | **아니다** |
| 오버레이가 열려 있으면 | close watcher 가 소비하고 history 는 안 움직인다 | close watcher 를 우회하고 그냥 라우팅한다 |
| 근거 | 정의의 "a **user** can send", 알고리즘 진입점의 "the user agent **receives**" | 위 경로에 진입하지 않는다 |

표준이 정한 **우선순위**가 있다. 뒤로가기는 오버레이 닫기가 먼저고, history 이동은 그다음이다.

> "On platforms where a back button is a potential close request, no event is involved, so when the back button is pressed, the user agent proceeds directly to process close watchers. If there is an active close watcher, then that will get triggered. If there is not, then the user agent can interpret the back button press in another way, for example as a request to traverse the history by a delta of −1."

fallback 규정도 같은 구조다.

> "Otherwise, there was nothing watching for a close request. The user agent may instead interpret this interaction as some other action, instead of interpreting it as a close request."

> ⚠️ 명세가 `history.back()` 을 "닫기 요청이 아니다"라고 **문장으로 쓴 곳은 없다.** 배제는 정의(사용자 발신)와 알고리즘 진입점(UA 수신)의 구조에서 따라온다. 인용할 때 이 차이를 뭉개면 안 된다.

Android 는 이 우선순위를 UX 산문이 아니라 **API 상수**로 규정한다.

> "PRIORITY_OVERLAY — Priority level of `OnBackInvokedCallback`s for overlays such as menus and navigation drawers that should receive back dispatch before non-overlays."

> "All `PRIORITY_OVERLAY` handlers are called before any `PRIORITY_DEFAULT` handlers. Within each priority group, handlers are invoked in a Last-In, First-Out (LIFO) order — the most recently added handler is called first."

Compose 는 Esc 와 백을 **한 플래그로 묶는다.** 이름이 `dismissOnBackPress` 인데 설명이 Esc 까지 포함한다.

> "dismissOnBackPress: whether the popup can be dismissed by pressing the back or escape buttons on Android or the escape key on desktop."

## history 를 소비해 뒤로가기로 닫는 관행은 표준이 배격했다
CloseWatcher 가 생긴 이유가 바로 이 관행이다. explainer 의 "What developers are doing today" 절이 문제를 다섯 가지로 열거한다.

> "- This UI state is non-navigational, i.e., the URL doesn't and shouldn't change when opening a component.
> - It's very hard to determine when the component's state is popped out of history, because both moving forward and backward through history emit the same `popstate` event.
> - The `history.state` API, used to store the component's state, is rather fragile: user-initiated fragment navigation, as well as other calls to `history.pushState()` and `history.replaceState()`, can override it.
> - History navigation is not cancelable. Implementing "Are you sure you want to close this dialog without saving?" requires letting the history navigation complete.
> - **A shared component that attempts to use the history API to implement these techniques can easily corrupt a web application's router.**"

마지막 항목이 공용 디자인시스템 컴포넌트에 직결된다. DS 가 라우터를 건드리면 안 되는 이유를 표준 문서가 직접 말한다.

설계 판단도 남겨 뒀다.

> "on the web the history API is intimately tied to navigations, the URL bar, and application state. Using it for UI state is generally not great."

`popstate` 가 왜 부적합한지는 MDN 이 더 직설적이다.

> "the `popstate` event is near the end of the process to navigate to the new location. It happens after the new location has loaded (if needed), displayed, made visible, and so on"

> "As you can see, the `popstate` event is nearly the last thing done in the process of navigating pages in this way."

> "it is important to take into account that properties like `window.location` will already reflect the state change (if it affected the current URL), but `document` might still not."

즉 `popstate` 로는 **이미 이동이 끝난 뒤**에야 알 수 있다. 닫기 애니메이션이나 저장 확인을 붙일 자리가 없다.

## UI 상태와 내비게이션을 가르는 기준
explainer 가 SPA 에서 이 경계가 흐려진다는 점을 예시로 정리했다. 판정 기준으로 그대로 쓸 수 있다.

> "the line between "UI state" and "a navigation" can be blurry in single-page applications. ... this new-URL lightbox is a navigation, and it would not be suitable to use the `CloseWatcher` API for it, because closing it needs to update the URL back to what it was originally (i.e., navigate backwards in the history list)."

**닫으려면 URL 을 되돌려야 하는가.** 그렇다면 내비게이션이고 라우터가 정본이다. 아니라면 UI 상태이고 close request 로 다룬다. 조회 필터의 드롭다운은 후자다.

Ariakit 는 전자를 택했을 때의 배선을 예제로 보여준다. 라이브러리가 라우터를 감지하는 것이 아니라, 앱이 라우트를 상태의 정본으로 삼는 역방향이다.

> "To control the open state, you can pass the `open` and `onClose` props to the `Dialog` component. **These props allow you to synchronize the dialog state with other state sources, such as the browser history.**"

```jsx
const navigate = useNavigate()
<Dialog open onClose={() => navigate("/")} />
```

## light dismiss 는 포인터 이벤트만 본다
바깥 클릭 닫기도 표준 개념이다. 다만 트리거가 좁게 고정돼 있다.

> ""Light dismiss" means that clicking outside of a popover whose `popover` attribute is in the Auto or Hint state will close the popover. This is in addition to how such popovers respond to close requests."

알고리즘은 **신뢰된 `PointerEvent` 의 `pointerdown`/`pointerup` 쌍**만 받는다. 명세가 `isTrusted` 를 단정문으로 확인한다.

`popover` 속성의 세 상태가 이 정책을 값으로 노출한다.

| 값 | light dismiss | close request 응답 | 다른 팝오버를 닫음 |
|---|---|---|---|
| `auto` | 있음 | 있음 | 있음 |
| `hint` | 있음 | 있음 | hint 만 |
| `manual` | 없음 | 없음 | 없음 |

> ⚠️ `popover` 의 **invalid value default 가 `manual`** 이다. `popover="autu"` 처럼 오타를 내면 조용히 "아무것도 안 닫히는" 상태가 된다. 빈 값과 속성만 쓴 경우는 `auto`.

라우팅과의 관계는 세 갈래로 갈린다. **이 표가 이 문서의 출발점이다.**

| 상황 | 결과 | 근거 |
|---|---|---|
| Android 뒤로가기 | 닫힌다 | close request 경로. light dismiss 아님 |
| 실제 문서 전환 | Document 자체가 사라지므로 top layer 도 폐기 | "Documents have a top layer" |
| **SPA 라우팅 전환** | **플랫폼이 아무것도 하지 않는다** | 규정 자체가 없다 |

SPA 에서 라우팅 후 오버레이가 사라져 보이는 경우가 있는데, 라우팅이 닫은 것이 아니다. **라우터가 컴포넌트를 언마운트해서 노드가 DOM 에서 제거된** 것이다. 노드 제거는 별도 훅이 처리한다. 그래서 언마운트하지 않는 구조에서는 사라지지 않는다.

Navigation API 도 이 일을 맡지 않는다. 명세 문서를 기계적으로 대조하면 분업이 드러난다.

| 검색어 | `nav-history-apis.html` | `interaction.html` §6.10 |
|---|---|---|
| `popover`, `dialog` | 0건 | 정의 문장에 포함 |
| `CloseWatcher`, `close request` | 0건 | 절 제목 자체 |

라우팅 명세는 오버레이를 모르고, 오버레이 명세는 라우팅을 모른다. **그 사이에 남는 배선이 앱 몫이다.**

`navigate` 이벤트에 기대려 해도 구멍이 있다. 아예 발화하지 않는 경우가 명문화돼 있다.

> "the following navigations will not fire `navigate` at all: User-initiated cross-document navigations via non-back/forward browser UI, such as the URL bar, bookmarks, or the reload button ..."

## `dialog` 의 닫기 정책은 `closedby` 로 선언한다
같은 정책을 `<dialog>` 는 `closedby` 속성으로 노출한다. 기본값 계산이 함정이다.

> "The Auto state behaves as Close Request state when the `dialog` was shown using its `showModal()` method; otherwise the None state."

| 열기 방식 | 속성 없음 | `none` | `closerequest` | `any` |
|---|---|---|---|---|
| `showModal()` | Esc | 안 닫힘 | Esc | Esc + 바깥 클릭 |
| `show()` | **안 닫힘** | 안 닫힘 | Esc | Esc + 바깥 클릭 |

비모달 다이얼로그에 Esc 닫기를 주는 **유일한 선언적 수단**이 `show()` + `closedby="closerequest"` 다. 그런데 Safari 정식판이 아직 `closedby` 를 지원하지 않으므로 단독 의존은 안 된다. 모달은 Auto 가 Close Request 로 떨어져 `closedby` 없이도 Esc 가 동작한다.

명세가 `open` 속성 직접 조작을 경고하는 부분도 같이 봐야 한다.

> "it is generally better to never remove the `open` attribute manually. Instead, use the `requestClose()` or `close()` methods to close the dialog, or the `hidden` attribute to hide it."

## 지원 현황 (2026-09 기준)
| 기능 | Chrome | Firefox | Safari | caniuse |
|---|---|---|---|---|
| CloseWatcher | 126 (2024-06-11) | 149 (2026-03-24) | **정식 미지원** (STP 249) | 74.09% |
| `dialog closedby` | 134 (2025-03-04) | 141 (2025-07-22) | **정식 미지원** (STP 242) | 73.39% |
| Navigation API | 102, `intercept()` 는 **105** | 147 (2026-01-13) | 26.2 (2025-12-12) | 90.33% |

주의할 점이 셋 있다.

- **Chrome 은 CloseWatcher 를 120 에서 켰다가 껐고 126 에서 되살렸다.** 그리고 이 통합의 부수 효과가 크다. 릴리스 노트가 "Upgrades to `<dialog>` and `popover=""` to use the new close request framework, so that they respond to the Android back button" 이라고 적었다. 즉 **126 이전에는 Android 뒤로가기가 모달 다이얼로그를 닫지 않았다.**
- **Navigation API 는 인터페이스 존재와 실사용 가능 시점이 다르다.** BCD 의 Chrome 102 는 진입점만이고, `intercept()` 와 `canIntercept` 는 105 부터다. Baseline low 진입일은 2026-01-13 이다.
- **Baseline 진입이 무결함을 뜻하지 않는다.** Firefox 에 출하 후 열린 메타 버그가 있다. `1993238 [meta] Broken sites with Navigation API` 가 아직 NEW 다.

## 접근성 기준은 좌표가 아니라 생명주기를 요구한다
WAI-ARIA APG 는 닫기에 대해 **Escape 밖에 규정하지 않는다.** 8개 패턴 전문을 대조한 결과다.

| 계기 | APG 규정 |
|---|---|
| Escape | 있음. Combobox, Menubar, Dialog, Tooltip |
| 바깥 클릭 | **규범 규정 없음.** Dialog 의 About 절에 `typically`, `in some implementations` 로만 |
| 포커스 이탈 | Tooltip 의 onBlur 한 줄뿐 |
| 라우팅 전환, 뒤로가기 | **8개 패턴 전부 언급 0건** |

Listbox 는 Keyboard Interaction 절에 Escape 가 아예 없다. 독립 listbox 는 닫히는 대상이 아니기 때문이다.

APG 가 규범이 아니라는 것은 문서가 절 제목으로 못박는다. 절 제목 자체가 `APG is Not a Normative Standard`, `APG is not a UI Design System` 이다.

> "The APG does not specify normative requirements and thus does not have a conformance model."

> "The examples each represent a specific way of implementing one or more patterns; they are intended to be illustrative, not prescriptive."

> "because many aspects of the guidance are neither prescriptive nor comprehensive, readers may need to make decisions that require assessing tradeoffs that could impact users with disabilities."

키보드 규정의 근거도 규범이 아니라 관행이라고 밝힌다.

> "ARIA does not specify how specific keys should move focus inside of those widgets. So, the APG Task Force relies on broadly utilized keyboard conventions ... While those lists are not normative, the majority of such conventions are so well established that it is advisable to treat them as requirements."

**요구가 실제로 있는 곳은 WCAG 다.** SC 2.4.11 Focus Not Obscured 가 좌표가 아니라 생명주기를 요구한다. 지문은 가림 금지지만, Understanding 문서가 비영속 오버레이의 관행을 정의하면서 닫힘 시점을 규정한다.

> "The common trait of all these components is that they are not expected to persist after being acted on or once they are no longer the primary point of user interaction. Such non-persistent disclosures do not fail this SC since they do not obscure the item with focus. **However, if an author allows such components to persist after the user has 1) activated one of the opened items or 2) moved the focus away from the triggering item and the additional content, it is at risk of failing this criterion** by obscuring the item with focus."

> "this note is not intended to apply to disclosures that are by convention non-persistent. As discussed in the following sub-section, **an open dropdown that does not close when no longer focused is not following this convention.**"

설계 옵션으로 제시된 문장이 요구를 가장 직접적으로 표현한다.

> "When focus leaves the additional content, the additional content is automatically hidden or collapsed, or the content can be hidden or collapsed by use of a dedicated keyboard command (for example, the Escape key.)"

모달과 비모달의 갈림도 같은 문서에 있다.

> "A dialog-like overlay that does not take focus on appearance and does not either constrain interaction to the overlay or dismiss itself on loss of focus (thus allowing focus to exit into the content behind it) will be at risk of failing this SC"

SC 1.4.13 Content on Hover or Focus 의 Dismissible 요건은 적용 범위가 좁다. hover 나 focus 로 뜨는 것에만 적용되고, 클릭으로 여는 피커는 대상이 아니다. 면제 조건 둘이 있다.

> "The additional content communicates an input error message ... The additional content does not replace or obscure other meaningful content (including the trigger element itself)"

> ⚠️ **라우팅 전환이나 뒤로가기 시 오버레이를 닫으라고 요구하는 WCAG 성공 기준은 없다.** WCAG 2.2 규범 문서에서 `dismiss` 는 1.4.13 안에서만 등장한다. 2.4.11 이 요구하는 것은 포커스 기준의 생명주기이고, 라우팅은 그 범위 밖이다.

## 플랫폼 가이드라인은 요건이 아니라 기대치로 쓴다
Apple HIG 는 팝오버 닫기를 **기본 동작 + 예외**로 서술한다.

> "a popover generally closes when people click or tap outside its bounds or select an item in the popover. If multiple selections are possible, make sure the popover remains open until people explicitly dismiss it or they click or tap outside its bounds."

실수로 닫히는 경우를 전제로 한 규칙도 있다. 다중 선택 필터 드롭다운에 그대로 적용된다.

> "Always save work when automatically closing a nonmodal popover. People can unintentionally dismiss a nonmodal popover by clicking or tapping outside its bounds. Discard people's work only when they click or tap an explicit Cancel button."

Sheets 문서에는 뒤로가기 버튼의 역할을 못박은 문장이 있다.

> "The Back button lets people navigate to a previous step in a multi-step flow or to a parent view in a hierarchy. **It isn't intended to dismiss a sheet.**"

Material 3 는 컴포넌트마다 다르다.

| 컴포넌트 | 시스템 백으로 닫기 | 위치 |
|---|---|---|
| Menus | 있음. "Using the system back button" | **Accessibility 탭** (Guidelines 탭에는 없음) |
| Dialogs | 공개 문서에 **없음** | 아래 주 참고 |
| Bottom sheets | 닫기 목록에 **없음**. predictive back 은 애니메이션 관점으로만 | Guidelines |

> 💡 M3 다이얼로그의 CMS 페이로드에는 시스템 백을 포함한 닫기 목록이 들어 있지만 `isHidden: true` 이고 렌더링되는 세 탭 어디에도 나오지 않는다. 반면 Material 2 다이얼로그는 같은 목록을 공개 문서에 명시했다. 근거로 인용할 때 이 차이를 밝혀야 한다.

표현도 요건이 아니다. M2/M3 다이얼로그는 `may be dismissed by`, M3 메뉴는 `People expect to exit a menu by` 다. `must` 나 `required` 로 시스템 백 닫기를 규정한 문장은 세 컴포넌트 어디에도 없다.

## 숨기기는 닫기가 아니다
여기가 실무에서 가장 많이 틀리는 지점이다. **top layer 와 포털은 서로 다른 축을 탈출한다.**

| | top layer (`dialog`, `popover`) | 포털 (`createPortal` → `body`) |
|---|---|---|
| 원래 조상의 `overflow`, `transform`, `opacity` | 벗어난다 | 벗어난다 (노드가 이동했으므로) |
| 원래 조상의 `display: none`, `hidden` | **벗어나지 못한다** | **벗어난다** |
| 새 부모(포털 대상)의 `overflow`, `transform` | 해당 없음 | **갇힌다** |

top layer 쪽 근거는 CSS Position 4 의 규정 목록에 명문으로 있다.

> "**If it is an element, it and its `::backdrop` pseudo-element are not rendered if its shadow-including inclusive ancestor has the `display: none`.**"

같은 목록의 Note 는 `overflow`, `opacity`, `mask` 는 조상이 영향을 못 준다고 하는데 `display` 는 그 목록에 없다. 자주 오독되는 문장이 바로 뒤 Note 다.

> "Note: This special rendering behavior ensures that elements in the top layer cannot be clipped by anything in the document, or obscured by anything except elements later in the top layer."

"regardless of what their ancestor elements might be doing" 로 이어지지만, 문면상 대상은 **clip 과 obscure 뿐**이고 박스 생성은 다루지 않는다.

포털 쪽은 반대다. `createPortal` 은 DOM 노드를 실제로 다른 위치에 삽입하므로 CSS 관점에서 부모가 바뀐다. React 문서가 경계를 정확히 그어 준다.

> "A portal only changes the physical placement of the DOM node. In every other way, the JSX you render into a portal acts as a child node of the React component that renders it. For example, the child can access the context provided by the parent tree, and events bubble up from children to parents according to the React tree."

React 가 컴포넌트 트리 기준으로 유지하는 것은 **context 와 합성 이벤트 전파**뿐이다. 상속과 박스 생성과 컨테이닝 블록은 전부 문서 트리를 따른다. 그래서 **포털은 CSS 조상으로부터의 탈출이 아니라 다른 CSS 조상으로의 이동**이다.

이 조합이 만드는 버그가 있다. 화면을 언마운트하지 않고 래퍼에 `hidden` 만 붙여 감추는 구조에서, 포털로 `body` 에 렌더된 드롭다운은 **감춰지지 않고 이전 화면 위에 그대로 남는다.** 열림 상태도 컴포넌트가 살아 있으니 유지된다. `hidden` 이 UA 스타일시트로 `display: none` 이 되지만, 그 규칙이 미치는 범위는 자기 서브트리뿐이다.

```css
[hidden]:not([hidden=until-found i]):not(embed) { display: none; }
```

> ⚠️ `!important` 가 없어서 저자 CSS 로 덮인다. 명세가 직접 경고한다. "a rule that applies 'display: block' to all elements will cancel the effects of the Hidden state."

**조용히 실패하는 조합도 있다.** `showModal()` 과 `showPopover()` 의 전제 조건은 연결 여부만 검사하고 렌더링 여부는 보지 않는다. 조상이 `display: none` 인 상태에서 호출하면 예외 없이 성공하고 `open` 도 붙고 top layer 에도 들어가지만 화면에는 아무것도 없다. 모달이면 문서가 inert 가 되어 **화면은 그대로인데 클릭만 막히는** 상태가 만들어진다.

## 라이브러리는 포털 대상과 닫기 계기를 앱에 넘긴다
포털이 필요한 이유는 클리핑과 쌓임 문맥 탈출이다. Floating UI 가 가장 명확하게 적었다.

> "This is necessary to ensure the floating element can appear outside any potential parent containers that cause clipping (such as `overflow: hidden`), while retaining its location in the React tree."

그런데 **`body` 가 항상 정답은 아니다.** 그래서 거의 모든 라이브러리가 대상을 바꿀 탈출구를 둔다.

| 라이브러리 | 프롭 | 기본값 |
|---|---|---|
| MUI | `container`, `disablePortal` | `document.body`, `false` |
| Ant Design | `getPopupContainer` | `() => document.body` |
| Radix UI | `Popover.Portal` 의 `container` | `document.body` |
| Base UI | `Popover.Portal` 의 `container` | 표기 없음 |
| Chakra UI | `Portal` 의 `container`, `disabled` | 표기 없음 |
| React Aria | `UNSAFE_PortalProvider` | 없음 |
| Floating UI | `FloatingPortal` 의 `root`, `id` | `document.body` |
| Headless UI | **없음** | 포털 고정 |

왜 제공하는지를 밝힌 정본은 Ant Design FAQ 다.

> "How do I prevent `Select Dropdown DatePicker TimePicker Popover Popconfirm` scrolling with the page? Use `<Select getPopupContainer={trigger => trigger.parentElement}>` to render a component inside the scroll area."

Chakra 는 반대 방향의 금지를 적었다.

> "When nesting floating elements like popover, select, menu, inside of the popover, avoid portalling them to the document's body."

**상충 관계를 가장 솔직하게 적은 곳은 React Aria 다.** 프롭 이름에 `UNSAFE_` 를 붙였다.

> "`UNSAFE_PortalProvider` is considered `UNSAFE`. Some portal locations may not work with styling, accessibility, or for a variety of other reasons. Typically, it is best to portal to the root of the entire application, e.g. the `body` element, outside any possible overflow or stacking contexts."

포커스 쪽 대가를 구체적으로 드러낸 곳은 Floating UI 의 `preserveTabOrder` 다. DOM 트리가 아니라 React 트리 기준으로 탭 순서를 유지한다는 설명 자체가, 포털이 DOM 순서와 논리 순서를 어긋나게 만든다는 것을 전제한다. Headless UI 는 반대로 포털 고정의 편익을 접근성으로 설명한다.

> "Because of accessibility concerns, the `Dialog` component is automatically rendered in a portal under-the-hood."

모달 안에서 포털 대상을 어떻게 판정하는지는 → [캘린더.md](./캘린더.md#포털-대상--body-로-고정하면-모달-포커스-트랩-밖으로-나간다)

닫기 계기도 같은 방식으로 쪼개서 넘긴다. Floating UI `useDismiss` 의 기본값이 사실상 업계 표준형이다.

| 프롭 | 기본값 | 계기 |
|---|---|---|
| `escapeKey` | `true` | Esc 키 |
| `outsidePress` | `true` | 플로팅과 트리거 밖을 누름 |
| `referencePress` | `false` | 트리거를 누름 |
| `ancestorScroll` | **`false`** | 오버플로 조상을 스크롤 |

`onOpenChange` 의 `reason` 유니언이 이 라이브러리가 인지하는 사유의 전부다.

```ts
type OpenChangeReason =
  | 'outside-press' | 'escape-key' | 'ancestor-scroll' | 'reference-press'
  | 'click' | 'hover' | 'focus' | 'list-navigation' | 'safe-polygon'
```

Radix 는 콜백으로 노출한다. `onEscapeKeyDown`, `onPointerDownOutside`, `onFocusOutside`, `onInteractOutside` 네 개다. 배치와 닫기 계기를 모두 앱 결정 사항으로 열어 둔 것이다.

**어느 쪽에도 라우팅 항목이 없다.** Floating UI 는 문서 전수 검색 결과 라우팅을 모델링조차 하지 않고 `OpenChangeReason` 에 해당 항목이 없다.

## 라우트 전환 시 닫기는 앱 책임이라는 데 모두 일치한다
헤드리스 라이브러리들의 공식 입장을 모으면 방향이 하나다.

| 라이브러리 | 입장 |
|---|---|
| **Radix UI** | 앱 책임. 메인테이너가 "hook into router events and `setOpen(false)`" 라고 답변. 다른 스레드에서 "watch for a router change and then set the component to close?" 라는 질문에 "Yes" |
| **Headless UI** | 컴포넌트별로 갈린다. Menu 는 라이브러리가 닫고, Popover 는 "we can't automatically close them". 라우트 변경 구독은 범위 밖 |
| **Base UI** | 링크 아이템은 기본 미닫힘. `Menu.LinkItem` 과 `NavigationMenu.Link` 의 `closeOnClick` 기본값이 `false` 라 앱이 옵트인한다 |
| **Ariakit** | 라우트를 오버레이 상태의 정본으로 삼도록 앱이 배선 |
| **React Aria** | `RouterProvider` 의 범위는 `href` 링크 내비게이션뿐. 오버레이 관련 단어 자체가 문서에 없다 |
| **표준** | Navigation API 의 비목표. 닫기는 close request 소관 |

Radix 는 링크 클릭 닫기를 컴포넌트에 내장하려 시도했지만(PR #1347) 래퍼 링크가 무력화한다.

> "`next/link` is overriding the default click handling added in that change which is why you're not seeing it working in your example."

Headless UI 도 같은 문제를 문서에 적었다.

> "By default, the `Menu` will close when clicking a `MenuItem`. However, **some third-party `Link` components use `event.preventDefault()` which prevents the menu from closing.**"

그리고 메인테이너의 전제가 드러나는 답변이 있다.

> "I'm trying to understand why this isn't working already? If you click a link to change a route, then it should already close because it is considered an "outside click". Are you doing programatic redirects without any user interaction at all?"

**"링크 클릭은 바깥 클릭이니 이미 닫힌다"가 전제다.** 프로그래매틱 내비게이션과 브라우저 뒤로가기는 이 전제 밖이다. 둘 다 포인터 이벤트를 만들지 않는다.

React Aria 의 `RouterProvider` 는 범위가 링크로 한정된다.

> "The `RouterProvider` component configures all React Aria components within it to navigate using the client side router you provide. ... any React Aria component with the `href` prop will automatically navigate using your router."

문서 전문에 `close`, `dismiss`, `overlay`, `Popover`, `Dialog`, `Modal` 이라는 단어가 없다. 게다가 리드 메인테이너가 폐기 방향을 선언했다.

> "This was removed intentionally. **RouterProvider is basically deprecated.** It is replaced by the recommendation currently shown in the docs to use the `render` prop with your router's Link component directly."

## 근본 원인은 공유 레이아웃과 캐싱이다
Base UI 이슈에 사용자가 남긴 한 줄이 이 주제의 본질을 짚는다.

> "The Menu also has `closeOnClick` which is missing from Navigation Menu (but important if your nav menu is, for example, **in your Next.js layout where its state persists when clicking a link**)."

오버레이가 라우트 전환에서 언마운트되지 않는 위치에 있으면 `open` 상태가 살아남는다. 공유 레이아웃이 그렇고, 화면을 캐싱하는 keep-alive 구조가 그렇다.

### React `<Activity>` 는 effect 를 버리고 state 를 남긴다
React 19.2(2025-10-01)에서 안정화된 `<Activity>` 가 이 구조를 공식 기능으로 만들었다. `mode="hidden"` 의 동작이 문서에 정확히 적혀 있다.

> "When an Activity boundary is hidden, React will visually hide its children using the `display: "none"` CSS property. It will also destroy their Effects, cleaning up any active subscriptions."

> "When the boundary becomes visible again, React will reveal the children with their previous state restored, and re-create their Effects."

| 항목 | hidden 일 때 |
|---|---|
| DOM | 유지되고 `display: none` |
| effect | **파괴됨** |
| state | 보존됨 |
| 재렌더링 | 낮은 우선순위로 계속 발생 |

Troubleshooting 절이 개념을 못박는다.

> "**Conceptually, the children are unmounted, but React saves their state for later.**"

**effect 를 버린다는 것이 핵심 설계다.** React Working Group 의 설계 문서가 이유를 오버레이로 직접 설명한다.

> "**It wouldn't make sense for an unmounted component to trigger some imperative code (e.g. to position a tooltip). The same is true for a component that's been hidden.** So React needs to tell the component that it is being hidden. How? By calling the same functions that it calls when the component is unmounted"

즉 프레임워크가 제공하는 keep-alive 는 숨길 때 정리 함수를 부른다. **`<div hidden>` 으로 감싸는 손수 만든 keep-alive 는 그것을 하지 않는다.** effect 도 구독도 그대로 살아 있다. 둘을 같은 것으로 보면 안 된다.

그런데 `<Activity>` 조차 포털은 놓친다. 문서가 DOM 보존의 부작용을 경고한다.

> "**Most notably, since a hidden component's DOM is not destroyed, any side effects from that DOM will persist, even after the component is hidden.**"

그리고 포털은 별도 이슈로 등록됐다. [react/react#35000](https://github.com/react/react/issues/35000), 2025-10-28.

> "React's `<Activity>` component does not hide portals when they are nested under another element. Only direct portal children are hidden, causing inconsistent behavior."

원인은 코어팀이 [PR #35091](https://github.com/react/react/pull/35091) 에서 정확히 서술했다. 이 문장이 이 문서 전체의 요약이기도 하다.

> "usually we only hide the direct DOM children of the Activity boundary. There's no reason to go deeper than that, because hiding a parent DOM element effectively hides everything inside of it. **Portals are the exception, because they don't exist in the normal DOM hierarchy; we can't assume that just because a portal has a parent in the React tree that it will also have that parent in the actual DOM.**"

**책임 경계를 두고 방향을 바꾼 기록**도 같은 PR 에 남아 있다. 규약을 논할 때 인용할 만한 대목이다.

> "**Previously we had intentionally chosen not to implement this behavior, because it was thought that this concern should be left to the userspace code that manages the portal**, e.g. by adding or removing the portal container from the DOM. ... **However, React does own the _contents_ of the portal, and we can hide those elements regardless of what the user chooses to do with the container.**"

즉 "포털 컨테이너는 앱 것이고 내용은 React 것"이라는 선으로 정리됐다. 컨테이너의 생명주기는 여전히 앱 몫이다.

> ⚠️ 이 수정은 **stable 에 아직 없다.** 19.2.1부터 19.2.8까지 릴리스 노트가 전부 서버 컴포넌트 항목이고 이 항목이 없다. 2026-09 기준 stable(19.2.8)에서는 `<Activity mode="hidden">` 안에 중첩된 포털 자식이 `body` 에 그대로 보인다. `19.3.0-canary` 계열에만 들어 있다.

### Vue `<KeepAlive>` 는 훅만 주고 정리는 앱에 남긴다
Vue 는 같은 구조를 훅으로 노출한다.

> "When a component instance is removed from the DOM but is part of a component tree cached by `<KeepAlive>`, it goes into a deactivated state instead of being unmounted."

> "its `activated` and `deactivated` lifecycle hooks will be invoked accordingly, providing an alternative to `mounted` and `unmounted`, which are not called. This applies to the direct child of `<KeepAlive>` as well as to all of its descendants."

Vue Router 와 쓸 때의 공식 패턴은 `RouterView` 슬롯 안에 넣는 것이다.

> "When working with the KeepAlive component, we would usually want it to keep the route components alive, not the RouterView itself. We can achieve that by putting the KeepAlive inside the slot"

```vue-html
<router-view v-slot="{ Component }">
  <keep-alive>
    <component :is="Component" />
  </keep-alive>
</router-view>
```

**Teleport 로 `body` 에 렌더한 오버레이를 어떻게 정리하라는 공식 안내는 없다.** `keep-alive.md` 에 `Teleport` 언급이 0건이고, `teleport.md` 에 `keep-alive` 언급이 0건이다. `onDeactivated` 문서도 콜백 등록 방법과 SSR 미호출 사실만 적는다.

대신 4년 넘게 열려 있는 버그가 있다. [vuejs/core#5603](https://github.com/vuejs/core/issues/5603), 2022-03-20 생성, 2026-09 현재 OPEN.

> "### What is expected? Modal's DOM removed.
> ### What is actually happening? Modal's DOM isn't removed."

코어팀 멤버의 유일한 답변이 해법의 위치를 알려준다.

> "**Manually disabled teleport is a workaround.**"

커뮤니티 표준 패턴은 앱이 `onActivated`/`onDeactivated` 로 `<Teleport :disabled>` 를 직접 토글하는 것이다. 공식 문서가 아니라 미해결 이슈 스레드에만 있다.

```vue
<template>
  <Teleport :disabled="!isActivated || props.disabled" :to="props.to">
    <slot />
  </Teleport>
</template>
```

**두 프레임워크의 결론이 같다.** 화면을 캐싱하는 기능은 제공하지만, 그 안에서 포털로 탈출한 오버레이를 정리하는 일은 앱에 남는다.

Floating UI 는 이 구조에 조건을 하나 붙여 뒀다. [팝오버배치.md](./팝오버배치.md#따라다니게-하는-비용--autoupdate)에 인용된 문장이다.

> "Only use this option if your floating element is _conditionally rendered_, not hidden with CSS."

즉 `whileElementsMounted: autoUpdate` 는 조건부 렌더링을 전제한다. CSS 로 숨기는 구조에서는 등록과 해제를 직접 관리해야 한다. **숨기기와 언마운트가 같지 않다는 것을 라이브러리 문서도 전제하고 있다.**

## 정리: 무엇이 표준 몫이고 무엇이 구현체 몫인가
**표준이 정해주는 것**

| 항목 | 내용 |
|---|---|
| 닫기 요청이라는 추상 | Esc, Android 백, AT 해제 제스처, 게임패드 백을 한 사건으로 묶음 |
| 우선순위 | 열린 오버레이가 뒤로가기를 먼저 소비, history 이동은 fallback |
| 이벤트 시점 | Esc 는 `keydown`, light dismiss 는 신뢰된 `pointerdown`/`pointerup` 쌍 |
| 스택 공유 | `dialog`, `popover`, `CloseWatcher` 가 한 스택 |
| 렌더 규칙 | top layer 는 클리핑을 벗어나지만 조상 `display: none` 은 못 벗어남 |
| 남용 방지 | history-action activation 으로 뒤로가기 가로채기 횟수 제한 |

**구현체가 정해야 하는 것**

| 항목 | 표준 상태 | 참고 |
|---|---|---|
| **SPA 라우팅 전환 시 닫을지** | 규정 없음. Navigation API 의 비목표 | 라이브러리 6곳 모두 앱 책임이라는 입장 |
| **포털 대상 DOM 위치** | 규정 없음 | 라이브러리가 `container` 계열로 위임 |
| **숨김 상태의 생명주기** | 규정 없음 | React 도 Vue 도 포털 정리는 앱에 남긴다 |
| **포털 컨테이너의 생명주기** | 규정 없음 | React 코어팀이 그은 선. 내용은 프레임워크, 컨테이너는 앱 |
| Esc 후 값 처리 | 규정 없음 | → [캘린더.md](./캘린더.md#esc-는-닫기만-같고-값-처리가-갈린다) |

**하지 말아야 하는 것**

- history 를 소비해 뒤로가기로 닫기. explainer 가 다섯 가지 이유로 배격했고, 공용 컴포넌트가 이걸 하면 앱 라우터를 망가뜨린다
- `popstate` 로 닫기 판정. 이동이 끝난 뒤에야 발화하고 전진과 후진이 같은 이벤트다
- `open` 속성을 직접 제거해서 닫기. `close` 이벤트가 안 나가고 이후 `close()` 로도 못 닫는다
- top layer 로 올리면 조상 `display: none` 을 벗어난다고 기대하기
