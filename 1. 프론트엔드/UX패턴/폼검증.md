# 폼 검증
유효성 문구를 **언제** 보여주고, 무엇으로 저장을 막을지에 대한 패턴

## 문구는 제출 시점에 보여준다
입력값이 조건을 어기는 순간 바로 오류 문구를 띄우면, **아직 입력을 끝내지 않은 사용자를 오류 상태로 몰아붙인다.**

- 이메일을 한 글자 칠 때마다 "올바른 이메일이 아닙니다"가 뜨는 화면이 이 경우
- 값을 지우는 순간 문구가 뜨는 것도 같다. 지우는 중일 수도 있다
- 그래서 기본은 **제출을 시도한 다음**에 알린다. 제출 = 사용자가 "다 썼다"고 선언한 시점

제출 이후에는 값을 고치는 즉시 문구가 사라지는 편이 좋다. 한 번 틀렸다는 걸 알게 된 뒤라 실시간 피드백이 도움이 된다.

> 💡 react-hook-form은 `mode: 'onSubmit'`(기본) + `reValidateMode: 'onChange'`(기본) 조합이 이 동작을 그대로 만든다. 시점 규칙과 한계는 [아래](#제출-이후에는-오류가-붙은-필드만-입력-중에-재검증한다)에서 이어 다룬다. → [react-hook-form.md](../라이브러리/react-hook-form.md)

예외를 둘 만한 경우
- **비용이 큰 실수** : 아이디 중복 확인, 비밀번호 규칙처럼 제출 후 되돌리기 번거로운 것은 blur 시점에 알려도 좋다
- **입력 형식이 좁은 필드** : 날짜, 전화번호처럼 형식이 하나뿐이면 입력 단계에서 마스킹·제한으로 막는 게 문구보다 낫다

## 제출 이후에는 오류가 붙은 필드만 입력 중에 재검증한다
"제출 전에는 침묵하고, 한 번 제출한 뒤에는 고치는 즉시 반응한다"는 이름이 붙은 패턴이다. **reward early, punish late** (Mihael Konjević, 2018)

| 그 필드의 직전 상태 | 검증 시점 |
|---|---|
| 오류 | 입력 중 (reward early) |
| 정상 | 필드를 벗어날 때 (punish late) |
| 제출 버튼을 누른 순간 | 모든 필드를 오류 상태로 취급하고 즉시 검증 |

- 이미 틀렸다는 걸 아는 사용자에게는 실시간 피드백이 도움이 된다. **고쳤다는 확인이 빨리 온다**
- 반대로 아직 멀쩡한 필드는 입력이 끝나지 않았을 수 있으니 늦게 말한다
- 오류가 풀린 필드는 다시 "정상" 취급으로 돌아가 blur 시점 검증이 된다

업계 표준으로 볼 근거
- Smashing Magazine의 라이브 검증 가이드가 이 패턴을 그대로 권한다. 키 입력마다 검증하는 것은 "이미 오류가 붙은 필드"에 한정하고, 빈 필수값은 제출 시점에만 알리라고 한다
- 폼 라이브러리도 이 패턴을 전제로 쓴다. react-hook-form은 재검증 대상을 "제출 이후 **오류가 있는** 입력"으로 설명한다(다만 실제 구현은 그보다 넓다 → [react-hook-form.md](../라이브러리/react-hook-form.md))
- re-formality는 검증 전략을 다섯 가지로 정리하면서, 어느 전략이든 **첫 피드백이 나간 뒤에는 모두 "값이 바뀔 때마다"로 넘어간다**고 못박는다

공공 디자인 시스템은 여기까지 가지 않는다
- GOV.UK는 첫 알림을 제출까지 미루라고 한다. "Do not validate when the user moves away from a field. Wait until they try to move to the next part of the service"이고, "avoid validating the information in a field before the user has finished entering it"이다
- CMS Design System도 기본을 제출 시점 검증으로 두고, 실시간 검증은 "답이 자명하지 않거나 입력이 어려운 필드"에 한해 조심해서 쓰라고 한다
- 다만 두 곳 모두 **제출 이후의 재검증 시점은 규정하지 않는다.** 위 패턴과 충돌하는 게 아니라 첫 알림 시점만 보수적으로 잡아둔 것이다

그래서 표준을 한 줄로 줄이면 "첫 알림은 제출 시점, 그 뒤로는 **오류가 붙은 필드만** 입력 중"이다. 제출한 뒤라도 정상인 필드는 여전히 blur까지 기다린다.

> 💡 폼 라이브러리 기본값이 이 패턴을 그대로 주지는 않는다. 어긋나는 지점과 필드별로 나누는 방법은 [react-hook-form.md](../라이브러리/react-hook-form.md) 참고.

## 오류 문구는 포커스를 받는 요소에 연결한다
화면에 오류 문구를 그렸다고 보조기술이 읽는 것은 아니다. 스크린리더는 **지금 포커스를 받은 요소의 설명(accessible description)** 을 읽기 때문에, 문구가 다른 자리에 떠 있으면 그 요소와 이어 두지 않는 한 존재 자체를 모른다.

연결은 `aria-describedby`로 한다. 오류 문구 요소에 `id`를 주고, 입력이 그 `id`를 가리키게 한다.

```html
<input id="dong" aria-invalid="true" aria-describedby="dong-error" />
<span id="dong-error">필수 입력 항목입니다.</span>
```

`aria-invalid`는 "틀렸다"는 상태만 말하고 **왜 틀렸는지는 말하지 않는다.** 둘은 같이 쓴다.

### 왜 aria-errormessage가 아닌가
오류 전용 속성인 `aria-errormessage`가 스펙에 있지만 실무에서는 `aria-describedby`를 쓴다. **VoiceOver와 NVDA가 `aria-errormessage`를 지원하지 않아서** 문구가 통째로 묻힌다. React Aria가 코드 주석에 이유를 남겨 뒀다.

> Use aria-describedby for error message because aria-errormessage is unsupported using VoiceOver or NVDA.

### 붙이는 자리는 "포커스를 받는 그 요소"다
가장 흔한 실수가 **래퍼에 붙이는 것**이다. 툴팁이나 팝오버 컴포넌트가 children을 `span`으로 감싸고 그 `span`에 `aria-describedby`를 붙이면, 포커스는 안쪽 `input`이 받으므로 보조기술은 아무것도 읽지 않는다. 화면에는 문구가 잘 보이고 DOM에도 속성이 있어서 눈으로는 멀쩡해 보인다.

주요 headless 라이브러리가 전부 같은 전제를 깐다. **개발자가 진짜 포커스 대상을 알고 거기에 직접 붙인다.**

| 라이브러리 | 전달 방식 |
| --- | --- |
| React Aria | `triggerProps`를 돌려주고 소비자가 spread |
| Radix | `asChild` + `Slot`으로 자식 요소에 병합 |
| Floating UI | `getReferenceProps()`를 돌려주고 소비자가 spread |
| Braid (vanilla-extract 진영) | render prop으로 `triggerProps`를 내려줌 |

컴포넌트가 자식 구조를 모르는데 붙여야 한다면, 속성을 직접 꽂지 말고 **id를 context로 내려보내 포커스 요소를 가진 쪽이 스스로 붙이게** 한다.

### 기존 describedby를 덮지 않는다
한 입력이 여러 설명을 가리킬 수 있다. 도움말 문구와 오류 문구가 동시에 있거나, 바깥에서 `aria-describedby`를 넘겨준 경우다. 공백으로 이어 붙이는 것이 공통 관행이다.

```ts
// React Aria useField
'aria-describedby': [descriptionId, errorMessageId, props['aria-describedby']]
  .filter(Boolean).join(' ') || undefined
```

Braid도 `mergeIds`로 같은 일을 하고, Radix는 여기에 `Set` 기반 중복 제거를 더한다. **참조 id는 그 요소가 실제로 렌더될 때만 건다.** 존재하지 않는 id를 가리키면 보조기술이 읽을 것을 찾지 못한다.

### 툴팁으로 오류를 띄울 때의 공백
행 높이가 밀리는 게 싫어 오류를 툴팁으로 띄우는 경우가 있는데, 툴팁은 보통 열려 있을 때만 DOM에 있다. 그러면 **스크린리더 가상 커서로 화면을 훑는 사용자는 그 문구를 만나지 못한다.** DOM에 남겨 두자는 제안이 오래 논의됐지만, 툴팁이 많은 화면의 성능 때문에 되돌려졌다. 현재 라이브러리들도 "열렸을 때만 연결"을 택하고 있으니, 이 공백은 감수하거나 문구를 시각적으로만 숨긴 요소로 항상 렌더해 해결한다.

### 확인은 DOM이 아니라 접근성 트리로 한다
`aria-describedby` 속성이 붙어 있어도 가리키는 요소가 `visibility: hidden`이거나 `display: none`이면 접근성 트리에서 빠져 읽히지 않는다. **속성 유무가 아니라 접근성 트리의 `description` 값**을 봐야 검증이 된다.

```js
// CDP 기준
await cdp('Accessibility.enable')
const ax = await cdp('Accessibility.getPartialAXTree', { nodeId })
// ax.nodes[0].description.value 에 오류 문구가 들어와야 통과
```

### 오류 요약 바는 별도로 알린다
필드마다 연결하는 것과, 저장 실패 시 상단에 뜨는 오류 요약을 알리는 것은 다른 문제다. 요약 바는 사용자가 포커스를 옮기지 않아도 나타나므로 **라이브 리전**이 필요하다.

- `role="alert"` 또는 `aria-live="assertive"` : 즉시 끼어들어 읽는다. 저장 실패처럼 바로 알아야 하는 것
- `aria-live="polite"` : 읽던 것을 끝내고 읽는다. 덜 급한 알림

GOV.UK와 CMS Design System은 요약을 **오류 문구 전문을 담은 링크 목록**으로 두고 제목에 포커스를 옮기라고 권한다. 링크를 누르면 해당 필드로 이동한다.

## 필수값 미입력으로 제출 버튼을 막지 않는다
필수값이 비었다는 이유로 버튼을 비활성하면 **막다른 길**이 된다.

- 버튼을 누를 수 없으니 왜 못 누르는지 알려줄 계기가 없다
- 화면 어딘가에 빈 필수 항목이 있다는 건 아는데, 긴 폼에서 그게 어디인지 찾아야 한다
- 비활성 버튼은 접근성 도구에서도 이유를 전달하지 못한다

버튼은 **진행 상태**로만 막는다.

| 막아야 하는 것 | 예 |
|---|---|
| 이미 처리 중 | 제출 요청 진행 중, 파일 업로드 중 |
| 보낼 것이 없음 | 변경 사항 없음, 선택된 항목 0건 |
| 권한·모드 | 읽기 전용 상세 화면 |

필수값은 눌렀을 때 막고, **어느 필드가 문제인지 그 필드 옆에서** 알린다.

## 필수 표시는 껐다 켜지 않는다
조건에 따라 필수가 되는 필드라도 라벨의 필수 표시(`*`)를 조건부로 토글하면, 사용자는 표시가 사라진 걸 알아채지 못하고 **표시가 깜빡이는 것으로만 느낀다.**

- 필수 표시는 **항상 켜두고**, 선택할 수 없는 상황이면 필드를 **잠근다(disabled)**
- 잠긴 필드에 필수 표시가 남아 있는 건 문제되지 않는다. "이 항목은 원래 필수인데 지금은 고를 게 없다"가 정확한 상태다
- 반대로 표시를 끄면 "지금은 안 써도 되나?"와 "이 항목은 원래 선택값인가?"가 구분되지 않는다

> ⚠️ 잠금(disabled)으로 검증까지 면제되지는 않는다. 폼 라이브러리에서 disabled는 보통 UI 상태일 뿐이고, 스키마 검증은 그대로 돈다. 조건부 필수는 스키마에 조건으로 써야 한다. → [react-hook-form.md](../라이브러리/react-hook-form.md)
