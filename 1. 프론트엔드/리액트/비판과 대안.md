# React 비판 읽기 (jsx.lol)

> 원문 : [jsx.lol — Does anybody actually like React?](https://jsx.lol) (David Bushell)
> 국내 소개 : ["React를 좋아하는 사람이 실제로 있긴 한가요?" - GeekNews](https://news.hada.io/topic?id=29900)

## 비판 6가지

### ① 자바스크립트를 너무 많이 보낸다

가장 자주 나오는 비판이고, 유일하게 숫자로 확인되는 비판이다.

React 앱은 화면을 그리는 일을 **사용자 기기**에서 한다. 문제는 서버는 우리가 좋은 걸 쓸 수 있지만 **사용자 기기는 고를 수 없다**는 것. 개발자 맥북에서 0.1초인 작업이 3년 된 보급형 안드로이드에서는 2초가 된다.

> "JS 중심 프로젝트는 광고보다 느리고, 시간이 갈수록 더 느려지고, 더 많은 노력을 요구한다" — Sérgio Gomes

Alex Russell(Microsoft Edge)은 이걸 *"측정 가능한 품질 위기"* 라고 부른다. 취향 문제가 아니라 실측 문제라는 뜻이다.

### ② 같은 일을 두 번 한다 (hydration)

Jeremy Keith가 한 줄로 요약했다.

> 서버에서 JavaScript로 계산해서 HTML을 주고, 그다음 **같은 JavaScript를 또 준다**

서버가 HTML을 그려서 보내면 화면은 바로 보인다. 그런데 버튼을 누를 수 있게 하려면 브라우저가 **같은 코드를 다시 실행**해서 이벤트를 붙여야 한다. 그 사이가 "보이는데 안 눌리는" 구간이다.

자세한 건 [프론트엔드 역사](../역사.md)의 ⑤번 레이어에 정리돼 있다.

### ③ 지켜야 할 규칙이 너무 많다

- 훅은 조건문 안에서 부르면 안 된다
- `useEffect` 의존성 배열을 틀리면 무한 루프거나 갱신이 안 된다
- 언제 `memo`를 씌워야 하는지 규칙이 명확하지 않다
- 서버 컴포넌트와 클라이언트 컴포넌트의 경계를 머릿속에 계속 들고 있어야 한다

David Bushell의 지적은 **"어려워서"가 아니라 "정답이 안 정해져서"** 에 가깝다.

> React의 실패는 **문서조차 우유부단한** 혼란스러운 API 설계로 증폭된다

10년째 "올바른 사용법" 논쟁이 안 끝나는 게 근거다.

### ④ 기본값이 되어버렸다 (frameworkism)

**이 비판의 대상은 React가 아니라 선택 과정이다.** 이걸 구분해야 나머지가 이해된다.

> 대화가 "실제 제약을 보고 도구를 고르자"가 아니라 **"React로 하죠"에서 시작한다** — Loren Stewart

> 우리의 실제 문제 중 React가 풀어주는 게 뭐가 있나? 목록을 훑었다. **하나도 없었다** — Kore Nordmann

> **프레임워크주의는 엔지니어링처럼 보이는 할 일을 준다. 실제로는 아니지만.** — Alex Russell

즉 "React가 나쁘다"가 아니라 **"React여야 할 이유를 아무도 안 따진다"** 는 비판이다.

### ⑤ Next.js / Vercel 종속

오픈소스인데 특정 회사의 플랫폼에서만 제 성능이 나온다는 지적. *"오픈소스로 위장한 벤더 락인"*(Abid Omar)이라는 표현까지 나온다. 셀프 호스팅하면 기능이 빠지거나 손이 많이 간다는 게 근거다.

### ⑥ 보안 — React2Shell

목록에서 **유일하게 의견이 아니라 사실인 항목**이다. 아래에서 따로 본다.

## CVE-2025-55182 (React2Shell) 쉽게 보기

### 무슨 일이 일어났나

서버 컴포넌트(RSC)는 서버와 브라우저가 **Flight**라는 전용 포맷으로 데이터를 주고받는다. 서버는 들어온 데이터를 다시 객체로 되살리는데(역직렬화), **이때 구조를 검사하지 않았다.**

공격자가 가짜 데이터 조각에 `then`이라는 메서드를 심어서 보내면, React가 그걸 **Promise인 줄 알고 실행해준다.** 그 순간부터 서버에서 공격자의 코드가 돈다.

비유하면 이렇다. 택배 상자를 열어보지도 않고 "송장에 Promise라고 적혀 있으니 Promise겠지" 하고 내용물을 그대로 실행한 것이다.

### 정리


| 항목     | 내용                                                                                  |
| ------ | ----------------------------------------------------------------------------------- |
| 등급     | **CVSS 10.0** (최고점)                                                                 |
| 조건     | 로그인 불필요, 사용자 클릭 불필요. **RSC 엔드포인트에 POST 한 번**                                        |
| 결과     | 서버에서 임의 코드 실행 (RCE)                                                                 |
| 영향 패키지 | `react-server-dom-webpack`, `react-server-dom-turbopack`, `react-server-dom-parcel` |
| 취약 버전  | 19.0.0 / 19.1.0~19.1.1 / 19.2.0                                                     |
| 패치 버전  | **19.0.1 / 19.1.2 / 19.2.1**                                                        |
| 공개     | 2025-12-03 (12-04 PoC 공개, 12-05 실제 공격 관측)                                           |


CVSS 10.0이 나온 이유는 **인증도 상호작용도 필요 없이 바로 코드 실행**까지 가기 때문이다. 10.0은 흔하지 않다.

### 우리 프로젝트는 해당되나

패키지 이름이 `react-server-dom-*`인 것만 해당한다. **서버에서 RSC를 돌리는 경우**에만 문제가 된다.

```bash
npm ls react-server-dom-webpack react-server-dom-turbopack react-server-dom-parcel
npm audit
```

- Next.js를 쓰면 간접 의존이라 **해당될 수 있다**
- Vite + React로 만든 CSR 전용 SPA는 이 패키지를 안 쓰므로 **해당 없다**

"React를 쓰니까 우리도 위험한가"가 아니라 **"서버에서 RSC를 돌리고 있나"** 로 판단하면 된다.

## 반대편도 봐야 한다

사이트가 스스로 편향을 밝힌 만큼, 안 담긴 쪽을 채워야 균형이 맞는다.

- **React가 실제로 푼 문제가 있다.** 데이터와 화면을 손으로 맞추던 시대를 끝냈다. GeekNews 댓글에도 *"React는 렌더링을 잘 추상화해서 UI 구현을 쉽고 빠르게 만들어줬다"* 는 반론이 있다.
- **욕하면서도 쓰는 데는 이유가 있다.** 댓글의 *"JS, SQL, PHP처럼 욕하면서도 쓰는 이유가 있지 않을까"* 가 핵심을 찌른다. 생태계(폼·데이터 페칭·컴포넌트 라이브러리)와 채용 시장이 전부 여기 몰려 있다.
- **대안에도 비용이 있다.** "Svelte로 3주 만에 재작성했다" 같은 사례는 그 앱이 3주 만에 재작성 가능한 규모였다는 뜻이기도 하다.
- **비판 중 상당수는 React가 아니라 Next.js/RSC를 향한다.** ②⑤⑥이 전부 그렇다. React를 SPA로 쓰는 것과 RSC를 서버에서 돌리는 건 위험도가 다르다.

## 그래서 실무에서는


| 상황                      | 판단                                                             |
| ----------------------- | -------------------------------------------------------------- |
| 콘텐츠 위주 사이트(블로그, 랜딩, 문서) | React가 안 필요할 가능성이 높다. Astro·HTML 우선                            |
| 상호작용이 많은 사내 도구·대시보드     | React가 여전히 합리적. 상태가 복잡할수록 이득                                   |
| 이미 React로 되어 있다         | **재작성이 답이 아니다.** JS 양 줄이기, 번들 쪼개기, 무거운 컴포넌트 걷어내기가 비용 대비 효과가 크다 |
| RSC/Next.js를 서버에서 돌린다   | 보안 업데이트를 남 일로 두면 안 된다                                          |


새 프로젝트를 시작할 때 던져볼 질문 네 개.

1. 이 화면에 **상태가 실제로 몇 개** 있나
2. 서버가 HTML을 그려주면 안 되는 이유가 있나
3. 사용자 기기가 어떤 것들인가 (사내 도구와 일반 소비자용은 다르다)
4. React를 고른 이유가 **"익숙해서"** 말고 있나

4번에 답이 있으면 그냥 쓰면 된다. 이 사이트가 하는 말도 결국 **"4번에 답을 해보라"** 다.

## 읽고 남은 생각

- 제목이 도발적이라 감정적인 자료처럼 보이지만, 실제 내용은 **"기본값으로 고르지 마라"** 한 줄이다. 도구 자체를 부정하는 글은 오히려 소수다.
- **의견과 사실을 갈라서 봐야 한다.** 성능·복잡도는 상황에 따라 다른 의견이고, CVE-2025-55182는 버전과 패치가 특정되는 사실이다. 같은 페이지에 섞여 있으니 무게가 같아 보이는 게 이 자료의 함정이다.
- [프론트엔드 역사](../역사.md)와 같이 읽으면 좋다. 그쪽이 "왜 이렇게 됐나"라면 이쪽은 "그래서 지금 뭐가 문제인가"다. 두 글 다 결론은 **서버 렌더링 + JS 최소화**로 같다.
- 이 사이트를 근거로 팀에 "React 버리자"고 말하면 설득력이 없다. **cherry-picked라고 본인이 써놨기 때문이다.** 쓰려면 여기 링크된 개별 글의 실측 데이터를 인용하는 쪽이 맞다.
