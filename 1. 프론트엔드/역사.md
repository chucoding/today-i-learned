# 프론트엔드 역사

> 원문 : [What happened to the frontend?](https://davidpoblador.com/deep-dives/what-happened-to-the-frontend/) (David Poblador i García, 2026-06)
> 국내 소개 : [당신이 안 보는 사이 프론트엔드에 무슨 일이 있었나 - GeekNews](https://news.hada.io/topic?id=31587)

## 2008년의 프론트엔드

- 서버(PHP 등)가 HTML을 만들어서 내려준다
- CSS는 손으로 쓴다
- 빌드 단계 **없음**. 파일을 FTP로 올리면 끝
- 페이지 일부만 바꾸려면 전체 새로고침

## 8개 레이어

### ① jQuery (2006–2010)

브라우저마다 DOM 메서드와 `XMLHttpRequest`가 달랐다. jQuery가 그 차이를 감추면서 AJAX가 대중화됐고, 처음으로 **페이지 일부만 갱신**할 수 있게 됐다.

남은 상처는 **수동 동기화**다. 자바스크립트 변수와 화면 요소를 각각 따로 갱신해야 해서, 하나만 빠뜨려도 화면과 데이터가 어긋났다.

> 이 레포의 [jQuery.md](./jQuery.md)에 있는 `cache: false` 같은 이야기가 이 시대의 잔재다.

### ② 프레임워크 (2010–2015)

"어디를 어떻게 바꿔라"(명령형) 대신 **"이 상태면 화면은 이렇게 생겼다"(선언형)** 로 뒤집었다. 동기화를 사람이 아니라 프레임워크가 한다.


| 프레임워크        | 특징                       |
| ------------ | ------------------------ |
| React (2013) | JSX, Virtual DOM diffing |
| Vue          | 진입장벽 낮음                  |
| Angular      | 엔터프라이즈 구조 + TypeScript   |
| Svelte       | 프레임워크를 컴파일로 걷어냄          |
| Solid        | Virtual DOM 없이 정밀 갱신     |


비용은 **런타임**이다. 0바이트·빌드 0단계였던 버튼이 React 런타임 45KB를 깔고 앉게 됐다.

### ③ 빌드 (2012–2018)

JSX도, `import`도 브라우저가 그대로 못 읽는다. 그래서 변환 단계가 생겼다.

- **Babel** — 미래 문법·JSX를 구형 브라우저용으로 변환
- **번들러(webpack 우세)** — 수백 개 파일을 몇 개로 합치고, 압축하고, 안 쓰는 코드 제거(tree shaking)
- **패키지 매니저(npm)** — 의존성 해결, `node_modules`

비용은 규모다. 기능은 작은데 `node_modules`에 **25만 개 넘는 파일**이 쌓인다.

### ④ 툴링 속도 경쟁 (2018–2024)

빌드가 90초를 넘고 webpack 설정이 전문 분야가 되자, 도구 자체를 컴파일 언어로 다시 짰다. 10~100배 빨라졌다.


| 도구         | 언어   | 대체 대상                              |
| ---------- | ---- | ---------------------------------- |
| esbuild    | Go   | 번들러                                |
| SWC        | Rust | Babel                              |
| Vite       | —    | 개발은 브라우저 네이티브 모듈 + HMR, 배포는 최적화 빌드 |
| Rolldown   | Rust | Vite의 프로덕션 번들러                     |
| pnpm / Bun | —    | npm                                |


> 이 시기 컨퍼런스 단골 멘트 : "Rust로 다시 짰더니 50배 빨라졌습니다."

### ⑤ 서버 렌더링 귀환 (2014–2026)

전부 자바스크립트로 그리다 보니, 첫 응답이 **빈 `<div>` + 거대한 JS 번들**이 됐다. 흰 화면이 뜨고, 검색엔진에는 아무것도 안 보인다. 그래서 **HTML을 서버에서 만들어 내려주는 2008년 방식으로 돌아갔다.**


| 약자  | 뜻                               | 언제 그리나            |
| --- | ------------------------------- | ----------------- |
| SSR | Server-Side Rendering           | 요청마다              |
| SSG | Static Site Generation          | 빌드 시점에 미리         |
| ISR | Incremental Static Regeneration | 미리 + 주기적 갱신       |
| RSC | React Server Components         | 서버에서만, JS 0바이트 전송 |


여기서 새로 생긴 상처가 **hydration**이다. 서버가 HTML을 그려 보내면, 브라우저가 **같은 자바스크립트를 다시 실행해서** 이벤트를 붙인다. 그 사이에 사용자는 화면은 보이는데 클릭이 안 먹는 구간을 만난다. 원문 표현으로는 *"같은 밥값을 두 번 내는 것"*.

완화 전략:


| 전략                | 대표    | 방식                        |
| ----------------- | ----- | ------------------------- |
| Islands           | Astro | 정적 페이지 + 상호작용 조각만 hydrate |
| Resumability      | Qwik  | hydration 자체를 건너뜀         |
| Server Components | React | 서버에서만 실행                  |


메타 프레임워크 : Next.js(React), Astro(콘텐츠 중심), SvelteKit, Nuxt(Vue), Remix/React Router

### ⑥ 엔지니어링 도구 (2015–2026)

- **TypeScript** — 원문은 2008년 이탈자 기준 *가장 큰 변화*로 꼽는다. 리팩터링을 겁내지 않게 해준다
- **Tailwind** — 마크업에 유틸리티 클래스(`class="px-4 py-2 rounded"`). 처음엔 논쟁거리였지만 지금은 생산성 표준
- **모던 CSS** — 네이티브 중첩, 변수, container query, `:has()`. **도구가 하던 일을 브라우저가 도로 가져갔다**
- **컴포넌트 라이브러리** — shadcn/ui는 설치하는 의존성이 아니라 **소스를 복사해 내 것으로 소유**하는 방식
- **데이터·상태** — TanStack Query, Zustand, Zod
- **테스트** — Vitest, Playwright

> 이 레포 기준으로는 [타입스크립트](./타입스크립트), [TanStackQuery](./TanStackQuery), [FSD](./FSD), [CSS 프레임워크](./CSS%20프레임워크) 문서가 전부 이 레이어에 속한다.

### ⑦ 배포 (2015–2026)

FTP로 파일 끌어다 놓던 것이 **git push → 자동 CI/CD**가 됐다. Vercel/Netlify/Cloudflare가 빌드·프리뷰·엣지 배포를 대신한다. 코드가 원본 서버 한 대가 아니라 사용자 근처 수백 개 데이터센터에서 돈다.

여기에 React Native/Expo(모바일), Tauri/Electron(데스크톱)까지 붙어서 같은 기술로 플랫폼을 넘는다.

### ⑧ AI 코드 생성 (2023–2026)

영어로 설명하면 동작하는 React 코드가 나온다(v0, Lovable, Bolt). 에디터 쪽은 Cursor, Claude Code, Copilot.

원문이 붙인 단서가 중요하다. **생성된 코드를 읽고 고치려면 결국 앞의 8개 레이어를 다 알아야 한다.** 백엔드 개발자가 반나절 만에 그럴듯한 프론트엔드를 만들 수는 있지만, 그게 이해를 대체하지는 않는다.

## 버튼 하나의 변천사

원문은 `<button>` 하나를 표본으로 각 시대를 비교한다.

```html
<!-- 2008 : 0바이트, 빌드 0단계 -->
<button onclick="addToCart()">Buy</button>
```

```jsx
/* 2013 : React 런타임 ~45KB */
function Buy() {
  return <button onClick={addToCart}>Buy</button>
}
```

```jsx
/* 2026 : 타입 검사 + hydration + 디자인 토큰 + 로컬 소유 */
<Button variant="default" size="sm" onClick={addToCart}>
  Buy
</Button>
```

소스는 **90바이트**인데 그걸 받치는 파일이 **25만 개**다. 이 격차가 이 글 전체의 요약이다.

## 결론 — 2008년으로 돌아왔다, 다만 나선으로

2026년의 최전선은 이렇다.

- 서버에서 HTML을 렌더링한다
- 자바스크립트는 최소로 보낸다
- 플랫폼 네이티브 API를 쓴다

2008년에 FTP로 올리던 그 파일과 결과물이 닮았다. 차이는 **성능 측정 도구, 타입 안정성, 접근성**이 붙었다는 것. 원점 회귀가 아니라 한 바퀴 돌아 위로 올라온 나선이다.

| 용도      | 조합                                                                             |

| 콘텐츠 사이트 | Astro + Tailwind + Vercel/Netlify/Cloudflare                                   |

## 읽고 남은 생각

- **도구를 배우는 순서보다 상처를 아는 순서가 중요하다.** webpack 설정을 외우는 것보다 "왜 번들러가 필요했나"를 아는 쪽이 오래 간다. 어떤 도구를 안 써도 되는지 판단할 수 있는 근거가 거기서 나온다.
- **되돌아온 것들이 있다.** 서버 렌더링, 그리고 전처리기가 하던 일을 가져간 모던 CSS. 유행을 늦게 따라가는 게 항상 손해는 아니다.
- **hydration은 아직 열린 상처다.** GeekNews 댓글에도 PHP4 → Vue2로 넘어갔다가 지금 Nuxt hydration 문제를 다시 만나고 있다는 이야기가 있다. Islands·Resumability·RSC가 전부 이 하나를 서로 다르게 우회하는 시도다.
- **⑧번 레이어가 앞의 7개를 없애주지는 않는다.** AI가 코드를 뱉는 속도가 빨라질수록, 그 코드가 어느 레이어의 어떤 상처를 건드리는지 읽어내는 쪽이 병목이 된다.
