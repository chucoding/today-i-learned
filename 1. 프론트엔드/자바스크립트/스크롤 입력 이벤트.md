## scroll 이벤트 출처 구분

- scroll 이벤트만으로는 사용자 휠 스크롤인지 코드의 `scrollTop` 변경인지 구분 불가
- 사용자가 스크롤을 시작할 때 먼저 생기는 입력 이벤트로 판별
  - `wheel` : 마우스 휠, 트랙패드 두 손가락 스크롤
  - `touchstart` : 터치스크린에 손가락이 닿는 순간
  - `pointerdown` : 마우스, 펜, 터치 공통 누름. 스크롤바를 잡고 끄는 경우까지 잡음.
- window 캡처 단계에서 passive로 받아 시각만 기록

```ts
const USER_SCROLL_INPUT_EVENTS = ['wheel', 'touchstart', 'pointerdown'] as const

USER_SCROLL_INPUT_EVENTS.forEach((type) => {
  window.addEventListener(type, () => { lastUserScrollAt = performance.now() }, { capture: true, passive: true })
})

// 키 입력보다 사용자 스크롤 입력이 더 최근이면 보정 건너뜀
if (lastUserScrollAt > lastKeyAt) return
```

- 쓰임 : 키 입력 직후 포커스 셀 가림을 보정하는 코드가 그 사이 휠 스크롤을 포커스 쪽으로 되미는 문제
  - 호출 경로로 보정을 제한했더니 가림이 다시 생김. 호출 경로가 아니라 입력 출처로 구분해야 했음.
- 한계
  - `pointerdown`은 셀 클릭에도 발생. 클릭 뒤 키를 누르면 키 시각이 더 최근이라 문제없음.
  - 키보드 PageDown, Space 페이지 스크롤은 잡지 못함.

## 코드로 바꾼 scrollTop 동기화

- 실측 사례 : MutationObserver 콜백 안에서 페이지 `scrollTop`을 바꾼 뒤 약 1초 동안 scroll 이벤트가 오지 않음.
  - scroll 이벤트에 맡긴 그리드 동기화가 그동안 268px 어긋난 채 남음.
- 해결 : scroll 이벤트를 기다리지 않고 `scrollTop`을 바꾼 직후 동기화 함수를 바로 호출

```ts
scroller.scrollTop += overflow
update()
```

- 400ms 간격 측정은 이 순간을 놓쳤고, rAF 루프로 프레임마다 기록하고서야 원인이 드러남.

## performance.now 기준 시각 초기값

- `performance.now()`는 페이지를 연 시점부터 잰 값
- `now - lastKeyAt < 1000` 판정에서 초기값이 `0`이면 페이지를 연 지 1초 안에는 키 입력 없이도 참
  - jsdom 단위 테스트에서 실제로 걸림 (테스트 시작 시점이 1000 미만)
- 초기값은 `Number.NEGATIVE_INFINITY`

```ts
let lastKeyAt = Number.NEGATIVE_INFINITY
```
