# 태그와 뱃지

## 표준 수단은 태그다. 뱃지는 코어에 없다

Storybook **8.4** 에서 태그가 사이드바 필터 UI 와 함께 정식으로 들어왔다. 필터는 코어 기능이라 애드온 없이 동작하지만, **태그를 뱃지로 보여주는 기능은 코어에 없다.** 공식 블로그가 이 경계를 분명히 한다.

> Badges require an addon — there's no native badge display.

즉 얻는 것과 별도로 사야 하는 것이 갈린다.


| 하고 싶은 것                   | 필요한 것   |
| ------------------------- | ------- |
| 사이드바에서 특정 성격의 컴포넌트만 추려 보기 | 태그만. 코어 |
| 목록에서 눈으로 구분되는 색 뱃지        | 애드온     |


### 내장 태그

기본으로 붙거나 특정 조건에서 자동으로 붙는 것들이 있다. 커스텀 태그를 지을 때 이름이 겹치지 않게 알아 둔다.


| 태그         | 기본 적용 | 뜻                                 |
| ---------- | ----- | --------------------------------- |
| `dev`      | O     | 사이드바에 렌더된다                        |
| `test`     | O     | 테스트 러너와 Vitest 애드온 실행에 포함된다       |
| `manifest` | O     | 컴포넌트·문서 매니페스트에 포함된다               |
| `autodocs` | X     | 문서 페이지에 포함된다                      |
| `play-fn`  | 자동    | play 함수가 있는 스토리에 자동으로 붙는다         |
| `test-fn`  | 자동    | 실험적 `.test` 메서드를 쓰는 테스트에 자동으로 붙는다 |


### 세 층위에서 선언하고 느낌표로 끊는다

`.storybook/preview`, 컴포넌트 meta, 개별 스토리 순으로 상속된다. 상위에서 내려온 태그는 `!` 접두어로 끊는다.

```typescript
// .storybook/preview.ts — 프로젝트 전체
export default { tags: ['autodocs'] }

// meta — 컴포넌트 단위
const meta = {
  component: SidePanel,
  tags: ['mui-structural'],
} satisfies Meta<typeof SidePanel>

// story — 개별 스토리에서 상속 해제
export const Sandbox: Story = { tags: ['!autodocs'] }
```

제약이 하나 있다. **태그는 정적 문자열이어야 한다.** 런타임에 만들어 넣을 수 없어서, 의존성 분석 결과 같은 것을 자동으로 붙이려면 코드젠으로 파일에 박아 넣는 수밖에 없다.

## 뱃지 애드온은 Storybook 메이저에 묶여 있다

뱃지는 매니저 UI 를 건드리는 영역이라 Storybook 메이저마다 깨진다. npm 레지스트리에서 확인한 peer 범위가 그 사정을 그대로 보여준다.


| 애드온                                      | 방식                                  | peer 이력                                                       | 상태                    |
| ---------------------------------------- | ----------------------------------- | ------------------------------------------------------------- | --------------------- |
| `storybook-addon-tag-badges`             | 태그를 그대로 뱃지로 렌더                      | 1.x → `storybook ^8.4.0`<br>`2.x → ^9.0.0`<br>3.x → `^10.0.0` | 활발. 다만 본선은 항상 최신 메이저뿐 |
| `@geometricpanda/storybook-addon-badges` | 태그가 아니라 `parameters.badges` 로 따로 선언 | 2.0.5 (2024-10) → `@storybook/* ^8.3.0`                       | 정체                    |
| `storybook-addon-status`                 | `parameters.status`                 | 1.0.1 (2021-03) → `@storybook/* ^6.1.21`                      | 사실상 폐기                |


여기서 나오는 실무 결론이 둘이다.

- **Storybook 을 8 에 묶어 두면 뱃지 애드온도 그 시절 버전에 묶인다.** `tag-badges` 1.4.0(2025-01)이 8.x 계열의 마지막이다. 새 기능은 2.x·3.x 로만 간다
- **태그는 코어라 이 문제가 없다.** 그래서 태그를 먼저 넣고, 뱃지는 정말 눈에 보여야 할 때 얹는 순서가 안전하다

### 태그 기반과 파라미터 기반

같은 뱃지라도 소스가 다르다.


|         | 태그 기반 (`tag-badges`)   | 파라미터 기반 (`geometricpanda`)               |
| ------- | ---------------------- | ---------------------------------------- |
| 선언      | `tags: ['deprecated']` | `parameters: { badges: ['deprecated'] }` |
| 사이드바 필터 | 코어가 태그를 알아서 필터에 노출     | 안 됨. 사이드바는 파라미터를 모른다                     |
| 상속·해제   | `!` 로 끊을 수 있음          | 객체 병합 규칙을 따름                             |
| 표현력     | 정적 문자열만                | 임의 객체 가능                                 |


필터가 목적이라면 태그 기반이 유리하다. **사이드바가 아는 메타데이터는 태그뿐**이기 때문이다.

## 업계는 "상태"를 표시하는 데 수렴했다

커스텀 태그로 무엇을 표시하느냐를 보면, 공식 문서와 디자인시스템 선례가 모두 **라이프사이클 상태** 한 축에 몰려 있다.


| 출처              | 값                                                          |
| --------------- | ---------------------------------------------------------- |
| Storybook 공식 예시 | `stable`, `experimental`, `alpha`, `deprecated`, 팀 소유, 완성도 |
| GitHub Primer   | Experimental / Ready / Deprecated                          |
| IBM Carbon      | Stable / Experimental(Preview) / Deprecated                |


세 곳의 어휘가 거의 같다. Primer 의 정의가 이 축이 무엇을 말하려는 것인지 잘 보여준다.

> **Ready**: "Breaking changes to these components will result in a major version bump in the component package and Primer will provide a migration path."

즉 상태 표시는 **"이걸 지금 써도 되는가, 깨지면 이사 경로를 주는가"** 에 답하는 축이다.

## 구현 가용성은 다른 축이다. 표준은 없지만 선례는 있다

"이 컴포넌트가 무엇에 묶여 있는가"는 상태와 다른 축인데, Storybook 생태계에는 이 축의 표준 태그 이름이 없다. 찾은 것은 디자인시스템 쪽 선례 하나다.

**IBM Carbon 의 컴포넌트 인덱스는 컴포넌트마다 React·Angular·Vue·Vanilla 아이콘 뱃지를 달아 어느 구현이 존재하는지 표시한다.** 표 형태의 매트릭스가 아니라 항목마다 붙는 작은 뱃지이고, 상세는 각 컴포넌트 페이지에서 관리한다.

정리하면 이렇다.


| 축         | 표준 여부           | 표현 방식           |
| --------- | --------------- | --------------- |
| 라이프사이클 상태 | 사실상 표준. 어휘까지 수렴 | 태그 + 뱃지         |
| 구현·의존 가용성 | 표준 없음. 선례는 있음   | 항목별 뱃지 (Carbon) |


그래서 "이 컴포넌트는 MUI 에 묶여 있다" 같은 표시를 하려면 **메커니즘은 빌려 쓰되 어휘는 직접 정의하고 문서에 남겨야 한다.** 남기지 않으면 다음 사람이 태그를 보고 뜻을 짐작한다. 의존을 한 덩어리로 보지 말고 성격으로 쪼개면 태그가 실제로 쓸모 있어진다. 동작 자체에 기대는 것과 레이아웃만 빌려 쓰는 것은 이식 비용이 다르다.

```typescript
tags: ['mui-structural']   // Drawer·Popover 등 동작에 의존. 걷어내려면 재구현
tags: ['mui-layout']       // Box·Stack 만. div 와 CSS 로 치환 가능
```

## 실제로 붙일 때 걸리는 것


| 함정                   | 내용                                                                    |
| -------------------- | --------------------------------------------------------------------- |
| 컴포넌트 항목의 태그는 **교집합** | 사이드바의 컴포넌트 줄에 뜨는 태그는 자식 스토리 전부가 공유하는 태그다. 스토리 하나에만 붙이면 컴포넌트 줄에는 안 보인다 |
| 사이드바 항목당 뱃지 **하나**   | 여러 태그가 매칭되면 우선순위가 가장 높은 뱃지 하나만 그려진다                                   |
| 스토리 단위 뱃지 커스터마이징 불가  | Storybook 구조상 애드온이 스토리별로 다른 뱃지를 낼 수 없다                                |
| 태그는 정적 문자열           | 빌드 타임에 값이 정해져 있어야 한다                                                  |
