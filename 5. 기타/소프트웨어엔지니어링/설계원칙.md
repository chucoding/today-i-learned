# 소프트웨어 3대 원칙

**DRY · KISS · YAGNI**. 셋 다 한 줄짜리 표어라 외우기는 쉬운데, 실무에서 갈리는 건 **셋이 서로 충돌할 때 무엇을 먼저 두느냐**다.

| 원칙 | 한 줄 | 언제 꺼내는가 |
|---|---|---|
| DRY | 같은 **지식**이 두 곳에 있으면 안 된다 | 이미 만든 걸 고칠 때 |
| KISS | 가장 단순한 해법을 고른다 | 만드는 방법을 정할 때 |
| YAGNI | 필요해지기 전엔 만들지 않는다 | 만들지 말지 정할 때 |

## DRY — Don't Repeat Yourself

『실용주의 프로그래머』(1999)의 정의는 "코드를 반복하지 마라"가 아니다.

> Every piece of **knowledge** must have a single, unambiguous, authoritative representation within a system.
> — 모든 **지식**은 시스템 안에서 하나의, 모호하지 않은, 권위 있는 표현을 가져야 한다

핵심 단어는 **knowledge**다. 지우라는 건 중복된 **코드**가 아니라 중복된 **결정**이다.

- 부가세율 10%가 세 파일에 흩어져 있다 → 진짜 DRY 위반. 세율이 바뀌면 세 곳을 고쳐야 하고, 하나를 빠뜨린다
- 두 함수의 생김새가 비슷하다 → **DRY 위반이 아닐 수 있다.** 우연히 지금 같아 보이는 것(coincidental duplication)

### 잘못된 추상화가 중복보다 비싸다

Sandi Metz의 문장이 이 원칙의 반대편을 정확히 짚는다.

> **duplication is far cheaper than the wrong abstraction**
> — 중복은 잘못된 추상화보다 훨씬 싸다

우연히 닮은 두 코드를 하나로 합치면 이런 경로를 밟는다.

```ts
// 1단계 — 비슷해 보여서 합친다
const validate = (value: string) => { /* ... */ }

// 2단계 — 한쪽 요구사항만 바뀐다. 플래그를 넣는다
const validate = (value: string, allowEmpty: boolean) => { /* ... */ }

// 3단계 — 또 갈라진다
const validate = (value: string, allowEmpty: boolean, trim: boolean, locale?: string) => { /* ... */ }

// 4단계 — 이제 아무도 이 함수를 못 건드린다
```

되돌리기도 어렵다. 중복은 눈에 보여서 나중에 합칠 수 있지만, 잘못 합쳐진 추상화는 호출부가 늘어날수록 풀기 어려워진다.

### 그래서 나온 대응책

| 이름 | 내용 |
|---|---|
| Rule of three | 세 번째로 같은 게 나왔을 때 추상화한다. 두 번째는 그냥 복사해 둔다 |
| AHA (Avoid Hasty Abstractions) | 성급한 추상화를 피하라. *"중복을 조금 참는 편이 낫다"* |
| WET | DRY를 비꼰 말. Write Everything Twice — 두 번까지는 써도 된다 |

**판단 기준** : 두 코드가 *지금* 같은가를 보지 말고, **앞으로 같은 이유로 같이 바뀌는가**를 본다. 같이 안 바뀔 거면 남남이다.

## KISS — Keep It Simple, Stupid

록히드 스컹크웍스의 Kelly Johnson이 남긴 말. 원래 맥락은 항공기 설계였다. **야전의 정비병이 기본 공구만으로 고칠 수 있어야 한다**는 요구였고, 설계자를 향한 욕이 아니라 "단순하게 유지하라"는 제약이었다.

여기서 자주 어긋나는 지점이 있다. **짧은 코드 ≠ 단순한 코드.**

```ts
// 짧다. 단순하지 않다
const label = a ? (b ? 'X' : c ? 'Y' : 'Z') : b ? 'W' : 'V'

// 길다. 단순하다
const getLabel = () => {
  if (!a) return b ? 'W' : 'V'
  if (b) return 'X'
  return c ? 'Y' : 'Z'
}
```

단순함의 기준은 **작성자가 아니라 6개월 뒤에 읽는 사람**이다. 영리한 한 줄은 쓸 때 기분이 좋고 읽을 때 시간을 잡아먹는다.

같은 이유로 이런 것들도 KISS 위반이다.

- 쓰지도 않는 유연성을 위한 설정 레이어
- 상태 관리 도구를 세 개 겹쳐 쓰기
- 상속 3단계를 타야 실제 동작을 알 수 있는 구조

## YAGNI — You Aren't Gonna Need It

XP(익스트림 프로그래밍)에서 나온 말. "언젠가 필요할 것 같아서" 미리 만드는 걸 막는다.

Martin Fowler가 정리한 **추측성 기능의 4중 비용**이 설득력 있다.

| 비용 | 내용 |
|---|---|
| cost of build | 만드는 데 든 시간. 안 쓰이면 통째로 낭비 |
| cost of delay | 그 시간에 만들었어야 할 진짜 기능이 밀린다 |
| cost of carry | 있는 동안 계속 읽히고, 이해되고, 리팩터링에 끌려다닌다 |
| cost of repair | 정작 필요해졌을 때 예상과 달라서 고쳐야 한다 |

마지막이 제일 아프다. 추측으로 만든 것은 **정작 요구사항이 오면 대개 안 맞는다.** 그러면 없느니만 못하다. 빈 땅에 짓는 것보다 잘못 지어진 걸 허물고 짓는 게 비싸기 때문이다.

### 가장 흔한 오용

YAGNI는 **추측성 기능**에 대한 원칙이지, 품질에 대한 원칙이 아니다.

| YAGNI 대상 | YAGNI 대상 아님 |
|---|---|
| 아직 요구되지 않은 기능 | 테스트 |
| "나중에 여러 DB 붙일지 모르니" 추상화 레이어 | 리팩터링 |
| 쓰는 데가 하나인데 만든 범용 옵션 | 에러 처리·보안·접근성 |
| 미래를 위한 설정값 | 이해하기 쉬운 코드 |

"테스트는 YAGNI잖아요"는 오용이다. 테스트는 **지금** 값을 낸다.

## 셋이 충돌할 때

| 충돌 | 상황 | 판단 |
|---|---|---|
| DRY vs KISS | 중복을 없애려다 구조가 복잡해진다 | **KISS 우선.** 추상화가 중복보다 이해 비용이 크면 남겨둔다 |
| DRY vs YAGNI | 나중에 재사용할 것 같아서 범용으로 만든다 | **YAGNI 우선.** 사용처가 하나면 그 자리에 둔다 |
| KISS vs YAGNI | 대체로 같은 편 | 둘 다 "지금 필요한 만큼만" |

적용 순서로 정리하면 이렇다.

1. **YAGNI** — 만들기 전에. 이거 지금 필요한가
2. **KISS** — 만들 때. 가장 단순한 방법이 이건가
3. **DRY** — 세 번째 중복이 나왔을 때. 이게 같은 이유로 같이 바뀌는가

DRY를 맨 뒤에 두는 게 핵심이다. 셋 중 **유일하게 되돌리기 어려운 실수를 만드는 원칙**이라서 그렇다.

## 프론트엔드에서 밟는 지뢰

**공통 컴포넌트를 너무 일찍 뽑는다.** 화면 두 개가 비슷하다고 `<CommonTable>`을 만들면, 화면이 다섯 개가 될 즈음 boolean prop이 열두 개 달린다. shadcn/ui가 **설치하는 의존성이 아니라 소스를 복사해 소유하는 방식**을 택한 것도 이 문제에 대한 답이다.

**커스텀 훅도 똑같다.** `useXxx` 두 개가 닮았다고 합치면 옵션 객체가 자란다. 두 훅이 서로 다른 화면의 요구로 갈라질 예정이면 남남으로 두는 게 맞다.

**우리 컨벤션에 이미 들어 있다.** `AGENTS.md`의 이 규칙이 정확히 AHA다.

> 기존 구현이 없으면 재사용 가능성이 명확한 경우에만 `shared/lib` 생성을 고려하며, 단일 사용 유틸은 사용처 가까이에 둔다.

**실제 판단 사례** — [react-hook-form reset](../../1.%20프론트엔드/라이브러리/react-hook-form.md) 건에서 통과한 해법이 세 개였는데, 두 개는 "reset을 부르는 모든 자리에서 그 필드를 손으로 되살린다"는 약속을 계속 지켜야 했다. `Controller`로 바꾸는 쪽은 지킬 약속이 없었다. **지켜야 할 규칙이 없는 쪽이 단순한 쪽**이라는 게 KISS의 실전 형태다.

## 읽고 남은 생각

- 세 원칙 중 **DRY만 방향이 반대다.** KISS와 YAGNI는 "하지 마라"인데 DRY는 "합쳐라"다. 그래서 초보일수록 DRY를 과하게 적용하고, 그 결과가 가장 오래 남는다.
- **"중복인가?"보다 "같이 바뀌는가?"** 가 실제로 쓸 수 있는 질문이다. 코드 모양이 아니라 변경 이유를 본다는 점에서 SRP(단일 책임)와 같은 이야기다.
- 원칙은 **판단을 대신해주지 않고 판단할 지점을 알려줄 뿐**이다. "DRY 위반입니다"로 끝나는 리뷰 코멘트보다 "이 둘이 같은 이유로 바뀌나요?"가 낫다.
- AI에게 코드를 시킬 때도 같다. 시키지 않으면 대개 **과하게 일반화된 코드**가 나온다. YAGNI는 사람보다 모델이 더 자주 어긴다.
