## 원칙

- **비공개 함수는 공개 API를 거쳐 테스트한다.** 내부 함수를 호출하는 공개 함수를 테스트하면 내부 함수도 함께 검증된다.
- **메서드가 아니라 동작을 테스트한다.** 사용자가 보는 동작이 그대로면 구현을 바꿔도 테스트는 바뀌지 않아야 한다.
- **테스트 때문에 공개 범위를 넓히지 않는다.** Guava는 public 선언에 `@VisibleForTesting`을 붙이는 것을 "나쁜 설계를 가리는 무화과 잎(fig leaf)"이라고 부른다. 테스트용으로 열어 둔 함수도 결국 다른 코드가 가져다 쓴다는 이유다.

## 종류

### 1. E2E 테스트

실제 사용자 흐름 확인

- 하나만 선택한다면 종단 간(E2E) 테스트를 우선함.
  - 실제 사용자 흐름을 검사
- 명확한 완료 기준과 구체적인 실패 지점을 제공
- CDP, 시뮬레이터, API 하네스를 활용하면 실제 실행 중인 시스템을 검증할 수 있음.

### 2. 속성 기반 테스트

깨지면 안 되는 제약 확인

- 사람이 예상한 실패 사례뿐 아니라, 사람이 놓치고 에이전트도 자주 실패하는 경계 사례를 탐색함.
- 항상 성립해야 할 조건을 작성한 뒤, [fast-check](https://fast-check.dev/)(JS/TS), [Hypothesis](https://hypothesis.readthedocs.io/en/latest/)(Python), [proptest](https://proptest-rs.github.io/proptest/)(Rust) 같은 라이브러리로 수천 개의 입력을 생성해 반례를 찾음
- 왕복 인코딩, 불변 조건, 멱등성, 동등성이 있음
  - **왕복 인코딩**: X를 인코딩한 뒤 디코딩하면 X가 나와야 하며, 파싱과 직렬화에도 적용 가능함
  - **불변 조건**: 계좌 잔액이 음수가 되지 않는 것처럼 항상 참이어야 함
  - **멱등성**: 마이그레이션, 정규화, 재시도를 두 번 수행해도 한 번 수행한 것과 효과가 같아야 함
  - **동등성**: 최적화한 코드가 단순하지만 올바른 코드와 같은 결과를 내야 함
- 특히 **명세와 프로덕션 동작이 어긋나**, 명세를 신뢰할 만한 검증 기준으로 삼기 어려운 재작성 작업에 유용함

### 3. 차등 테스트

기존 시스템을 정답 기준으로 활용

- 기능을 유지해야 하는 대규모 마이그레이션에 특히 효과적임.
- 기존 시스템과 새 시스템에 같은 입력을 넣고 결과를 비교하며, 차이가 생기면 버그나 호환성을 깨는 변경인지 확인하고 해결해야 함.
- **무작위 생성 입력**이나 프로덕션 트래픽 표본을 사용하고, 공백처럼 무관한 요소는 정규화함
- 새 환경에서 의도적으로 달라져야 하는 동작은 **승인된 변경 목록**으로 관리함

### 4. 스모트 테스트

새로운 빌드나 코드 변경 후 본격적인 테스트를 진행하기에 앞서, 핵심 기능이 정상적으로 작동하고 치명적인 오류가 없는지 빠르게 확인하는 초기 점검 테스트

- 전자 회로 기판에 전원을 켰을 때 연기가 나는지 확인하던 데서 유래
- 빌드가 추가 QA나 심층 테스트를 진행할 만큼 안정적인지 판단해 시간과 자원을 아낌
- 웹/앱 실행, 계정 및 인증, 핵심 트렌젝션(장바구니, 결제 등) 등
- 시뮬레이터 시작 방법이나 앱 실행 방법을 `verify` **스킬**로 작성하고, 저장소의 `.claude/skills/` 아래 관련 코드와 최대한 가까운 위치에 배치함
