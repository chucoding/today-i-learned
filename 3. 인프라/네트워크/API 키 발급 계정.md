# API 키 발급 계정(서비스 계정 vs 개인 계정)
API 키를 발급할 때 어떤 신원으로 발급하느냐의 차이. 개인 계정 키는 "사람"의 권한을 빌려 쓰는 것이고, 서비스 계정 키는 "프로그램" 자체에 부여된 독립된 신원이다.

## 비교

| 항목 | 개인(사용자) 계정 | 서비스 계정 |
|------|------------------|------------|
| 신원의 주체 | 사람 | 애플리케이션, 워크로드 |
| 권한 범위 | 그 사람이 가진 권한을 그대로 상속 | 필요한 권한만 별도로 부여 |
| 수명 | 퇴사나 권한 회수 시 함께 무효화 | 사람의 재직 여부와 무관 |
| 감사 로그 | "누가 했는지"로 기록 | "어느 서비스가 했는지"로 기록 |
| 인증 흐름 | 브라우저 동의 화면을 거치는 OAuth 3-legged | 사용자 개입 없는 2-legged(JWT, client credentials) |
| 할당량과 과금 | 사용자 단위 | 프로젝트나 조직 단위 |
| 보안 통제 | MFA, 비밀번호 정책 | 키 회전, 워크로드 아이덴티티 연동 |

## 실무에서 갈리는 지점

### 퇴사하면 서비스가 멈춘다
개발자가 자기 계정으로 키를 발급해 프로덕션 서버에 넣어두면, 그 사람이 팀을 떠나 계정이 비활성화되는 순간 배치와 API 호출이 전부 실패한다. 서비스 계정은 사람의 상태와 분리되어 있어 이 문제가 없다.

### 권한이 과도하게 열린다
개인 계정 키는 그 사람이 접근할 수 있는 모든 리소스에 접근할 수 있다. 관리자 권한을 가진 사람이 발급한 키가 유출되면 피해 범위가 조직 전체가 된다. 서비스 계정은 "이 배치는 특정 버킷 읽기만" 같은 최소 권한을 줄 수 있다.

### 로그를 믿을 수 없게 된다
개인 키를 서버에 심으면 감사 로그에 사람 이름이 찍힌다. 실제로는 자동화가 한 일인데 사람이 한 것처럼 보여서, 사고가 났을 때 원인 추적이 어려워진다.

### 접근 가능한 데이터의 성격이 다르다
Google Drive나 Gmail 같은 서비스에서 개인 계정 키는 그 사람의 개인 데이터에 닿는다. 서비스 계정은 자기가 소유한 리소스만 보는 것이 기본이고, 조직 구성원 데이터에 접근하려면 도메인 전체 위임(domain-wide delegation) 같은 별도 설정이 필요하다.

## 선택 기준

| 상황 | 선택 |
|------|------|
| 로컬 개발, 일회성 스크립트, 개인 도구 | 개인 계정 |
| 서버, CI/CD, 배치 작업, 프로덕션 | 서비스 계정 |
| 사용자 본인의 데이터를 대신 읽어야 하는 기능 | 개인 계정 기반 OAuth |

## 정적 키를 쓰지 않는 방향
서비스 계정 키 파일(JSON) 자체를 발급하지 않는 쪽이 권장된다. 키 파일은 유출되어도 만료가 없어 위험하기 때문에, 단기 토큰을 동적으로 받아 쓰는 방식이 표준이 되고 있다.

- GitHub Actions의 OIDC 연동
- GCP Workload Identity Federation
- AWS IAM Role

서비스 계정을 쓰되 정적 키 파일은 만들지 않는 형태다.
